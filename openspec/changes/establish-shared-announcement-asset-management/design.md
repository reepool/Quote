## Context

The repository already has a source-neutral `research.announcements` layer for CNInfo and exchange discovery, provider routing, normalized announcement/attachment records, conservative checkpoints, and governed byte retrieval. It intentionally stops before archive ownership. Business-profile consequently owns an immutable annual-report archive and `AnnualReportAssetCatalog`, while broker risk-control independently downloads the same formal reports, writes a different path, and mixes download state with parser state in `financial_source_files`.

Production data proves the ownership split creates duplicate files. Business-profile is also still under active rollout, so it cannot be the upstream producer on which unrelated consumers depend. The remounted `data/filings` volume has sufficient near-term capacity, but current database backup covers `data/*.db` rather than attachment files. The new capability must therefore centralize source assets, preserve business-specific parsing, adopt current files, and add independent scheduling and file operations.

Version 1 follows the user's latest-only retention policy: for an instrument and fiscal year, only the most effective annual-report attachment remains consumer-visible in the shared canonical archive after a verified complete correction replaces the original. A temporary, explicitly pinned legacy alias may preserve predecessor bytes for a consumer that has not cut over yet; it is migration debt, not a second effective asset, and must be removed after that consumer gate passes. Metadata, hashes, replacement lineage, processing history, and deletion audit remain. A predecessor backup retained solely for disaster recovery is not a second effective asset and cannot satisfy local-first access. Reconstructing a pre-correction historical PDF through normal local access is explicitly outside version 1.

Stakeholders include scheduler operations, research storage, business-profile, broker risk-control, DataManager/FastAPI clients, future announcement consumers, backup operations, and research users who require reliable source lineage.

## Goals / Non-Goals

**Goals:**

- Establish business-neutral announcement and attachment asset ownership.
- Bootstrap one latest effective annual report for every eligible active A-share stock that has a provably published report, and persist an explicit evidence-backed terminal coverage outcome for an eligible stock that legitimately has none.
- Run independent daily discovery and attachment maintenance after bootstrap.
- Prefer the latest verified complete correction and retain one physical effective annual report per instrument/fiscal year.
- Provide local-first lookup and bounded ensure/download for every consumer.
- Reuse valid files already under business-profile and broker archive roots.
- Separate source-asset validity from each consumer's parser and fact status.
- Integrate through DataManager, FastAPI, scheduler reporting, and consumer lineage.
- Add storage capacity, backup, integrity, retry, and deletion governance.
- Keep the model extensible to semiannual and other announcement types.

**Non-Goals:**

- Do not download every attachment for every announcement type in version 1.
- Do not move business-profile section selection, PDF extraction, LLM semantics, broker table parsing, or fact promotion into the asset service.
- Do not replace structured financial JSON/XBRL sources with annual-report PDFs.
- Do not preserve all superseded annual-report physical files for historical point-in-time reconstruction.
- Do not treat title similarity or identical content as sufficient to merge legal filing identities across sources.
- Do not require or depend on a Web frontend implementation; this project is intentionally AI/API-only and defines stable caller-visible API states.
- Do not perform any provider scan, attachment download, migration move/link/quarantine, durable work dispatch, or physical deletion during import or application, API, DataManager, or scheduler initialization. Startup may register dependencies and validate configuration only.

## Decisions

### Build an asset layer on top of `research.announcements`

Add a package such as `research/announcement_assets` with repository, service, annual-report policy, migration, and operation components. It consumes normalized announcement records and `AnnouncementAttachmentRetriever`; it does not implement provider HTTP logic.

```text
provider discovery / normalized records / safe byte retrieval
                           |
                           v
announcement asset repository and service
  metadata -> attachment observation -> blob -> effective annual report
                           |
                           v
consumer processing manifests and derived facts
```

Alternative: expand `BusinessProfileDocumentArchiveService` and let other consumers call it. Rejected because ownership and configuration would still depend on a non-production-ready business domain.

Alternative: put persistence directly into `AnnouncementAcquisitionService`. Rejected because metadata discovery and binary asset lifecycle have different retention, storage, concurrency, and failure semantics.

### Use separate canonical tables for metadata, blobs, policy, and processing links

The target model uses business-neutral structures conceptually equivalent to:

- `official_announcements`: source-qualified announcement identity, normalized/raw publication time, title, symbols, raw payload hash, first/last observed time, current metadata, provider route/diagnostic evidence, and an explicit source status.
- `official_announcement_attachments`: source-qualified attachment identity, URL metadata, media hints, and relationship to announcement.
- `official_document_blobs`: SHA-256, content length, media/signature state, canonical path, integrity state, first downloaded time, and verified backup state.
- `official_attachment_versions`: attachment observation plus content hash, final URL, retrieval evidence, validity, download attempt lineage, lease owner/generation, attempt/max-attempt, `next_retry_at`, error classification, and temporary/quarantine evidence. A `.part` path is never an effective asset path and its sidecar/age/byte state is reconciled separately from reservations.
- `effective_annual_reports`: instrument, fiscal year, report period, selected attachment version, correction flag, classification version, effective state, and replacement link.
- `official_annual_report_decisions`: append-only effective-decision history and replacement edges. Each transition retains instrument/fiscal-year scope, predecessor and replacement legal filing/attachment observation/blob identities, decision and policy versions, reason, activation time, and the matching outbox event key. The mutable effective row is only the current projection and cannot be the sole source of replacement lineage.
- `official_asset_operations`: durable discovery/download/backfill/on-demand operation state and leases.
- `official_asset_operation_subscriptions`: principal/consumer-scoped idempotency, authorization, response projection, and continuation links to a globally single-flight asset operation.
- `official_asset_deletion_intents`: durable `planned -> deleting -> deleted|failed` physical-deletion state, lease/generation, retries, and failure diagnostics.
- `official_asset_deletion_audit`: append-only physical deletion decisions.
- `official_asset_recovery_manifest`: immutable version 1 recovery entries for every correction predecessor or legacy duplicate before primary unlink, including prior legal/attachment identity, path/hash, replacement identity, backup object, verified file watermark, and reserved recovery pair id.
- `official_asset_recovery_pair_closures`: append-only verification that a recoverable catalog snapshot containing a manifest and the file-manifest watermark close the reserved pair id without rewriting the immutable manifest.
- `official_asset_backup_recovery_journal`: independently backed, integrity-chained post-snapshot catalog/outbox/operation/lineage/audit increments with predecessor and coverage watermarks for declared-RPO replay or truncation detection.
- `official_asset_change_events`: immutable monotonic outbox records committed atomically with effective-decision changes.
- `official_asset_consumer_checkpoints`: per-consumer idempotent delivery/replay position and failure evidence.
- `official_asset_consumer_processing`: optional shared index that links consumer/parser identities to source assets while consumer-owned manifests remain authoritative for domain outputs.

`announcement_audit` remains purpose-specific operational evidence and is not promoted into the canonical asset store. `financial_source_files` remains compatible for financial parser lineage but no longer owns physical annual-report identity.

Alternative: keep adding schema versions to `financial_source_files`. Rejected because the row identity and mutable status currently mix source files with parser purpose, preventing one source asset from supporting independent consumers cleanly.

### Keep four identities distinct

- Legal announcement: `source + source_announcement_id`.
- Attachment: `announcement_key + attachment_id`, or a deterministic normalized source-URL key when the provider lacks an attachment id.
- Physical content: SHA-256.
- Consumer processing: `asset_id + consumer + parser_version + parameter_hash`.

Identical bytes can share storage without merging legal identities. Equivalent cross-source candidates retain a stable sorted evidence set. A single `canonical_source_filing` projection is selected only through a versioned, discovery-order-independent projection policy; the effective decision and consumer lineage retain the policy version and evidence-set hash so a newly observed mirror cannot silently change processing identity. Cross-source mirrors require explicit evidence or policy before entering that equivalence set.

### Centralize a strict formal annual-report classifier

Version 1 accepts complete primary Chinese annual-report PDFs and complete corrected/revised annual-report PDFs. It excludes summaries, translations, visual editions, audit reports, inquiry material, correction notices without a complete replacement, and related announcements. Classification is attachment-level because one announcement can contain the full report, summary, translation, appendix, and notice together.

The classifier produces the canonical orthogonal vocabulary `document_family=annual_report|semiannual_report|...`, fiscal year/report period, `variant=original|correction`, `is_full_report`, reasons, and policy version. `correction` is a variant, not a peer document family, and a correction notice without a complete body remains evidence rather than an eligible corrected report. Provider categories and consumer legacy labels use versioned mappings into this vocabulary; they narrow discovery traffic but do not replace local fail-closed title/attachment classification.

Alternative: reuse business-profile classification through an import. Rejected because the shared service must own the common periodic-report subset; business-profile can layer specialist classifications downstream.

### Converge to one effective asset and delete predecessors safely

Winner order for one instrument/fiscal year is:

1. valid complete correction over valid original;
2. latest normalized publication time among complete corrections;
3. stable filing/attachment identity only inside a proven equivalent legal chain.

Cross-source candidates can converge automatically only when their content hash matches or governed mirror/legal-precedence evidence exists. Matching-byte candidates remain distinct legal filings in the effective decision's equivalence evidence set, while a versioned projection policy chooses any required single source-facing representative independently of discovery order. Different verified bytes with no precedence evidence are ambiguous, never resolved by lexical source or filing-id order. Withdrawal, cancellation, or a changed attachment under the same announcement id creates a new observation and triggers reevaluation.

The same fail-closed rule applies inside one source when publication timestamps have equal normalized value but different verified bytes: only an explicit replacement edge, official revision sequence, or other versioned legal-precedence evidence can choose a winner. Original timestamp values and precision are retained. A withdrawal affects a candidate only when provider status, target announcement/attachment identity, an official relation, or a versioned deterministic rule binds it to that candidate; generic withdrawal wording alone records unresolved evidence and cannot deactivate the current asset.

Attachment acquisition leases do not by themselves serialize the effective-version decision. Activation therefore uses an `instrument + fiscal_year` decision lease or row-version compare-and-swap, and reselects the winner from all committed observations inside the transaction. A worker that downloaded an older correction after a newer correction committed cannot downgrade the effective row or create a deletion intent for the true winner.

Replacement is a staged transaction:

1. discover and register correction metadata;
2. acquire the correction under an attachment lease;
3. validate source identity, PDF signature, byte length, SHA-256, and safe path;
4. in one database transaction activate the correction and persist its replacement edge, immutable replayable change-event outbox record, and, only when the predecessor is a distinct physical-unlink target, a `planned` deletion intent plus predecessor recovery-retention pin and reserved recovery pair id; a same-hash legal replacement records reference/audit state without a physical deletion intent;
5. after commit, deliver the outbox event and mark prior consumer processing stale/superseded or enqueue reprocessing;
6. remove the predecessor asset reference;
7. the backup required set includes every predecessor named by a `planned|deleting` intent even before its manifest row exists; after both predecessor and replacement are protected, persist the immutable version 1 recovery-manifest entry against the reserved pair id and verified file watermark, then create a catalog snapshot containing that manifest and append a separate verified pair-closure record;
8. delete the distinct predecessor blob only when all non-recovery/deletion-blocking physical retention pins are released and the backup/recovery-pair closure passes; the recovery pin must already have converted to a non-primary-blocking required-set hold;
9. transition the deletion intent through `deleting` to `deleted|failed` and let an idempotent reconciler recover crashes.

The old file remains effective if replacement validation or any activation-transaction write, including the outbox insert, fails. After activation commits, failed event delivery, consumer invalidation, backup, or unlink leaves a truthful pending/failed state and never rolls back the valid replacement. Delivery resumes from the durable outbox, and consumer checkpoints make replay idempotent; there is no state in which a committed replacement lacks a recoverable notification. Metadata and lineage are never deleted. A same-hash distinct filing transition cannot unlink its still-effective shared blob and therefore uses a non-applicable physical-deletion audit outcome. Physical retention pins include active assets, managed legacy aliases, not-yet-migrated consumers, and active read/processing leases; historical metadata references do not permanently pin bytes. Read and processing leases carry owner, TTL, heartbeat, generation, and a safety grace period. An expired lease releases its pin only through compare-and-swap reconciliation after no newer heartbeat is present; stale leases cannot pin bytes forever, but uncertain or live readers remain fail-closed deletion blockers. Unlink finalization revalidates the operation-captured approved mount identity and confirms absence on that same mount; a fallback-path absence can never finalize `deleted`. Configured predecessor-cleanup warning and hard ages make eventual convergence measurable: warning age degrades asset readiness, while hard age blocks the unique-storage completion claim and routes the intent to operator repair without rolling back the verified replacement or blocking unrelated verified reads.

A legally bound withdrawal uses the same serialized decision/outbox boundary. If a valid locally retained predecessor can become the winner, it is the replacement in the ordinary pair workflow. If no legal local replacement exists, the transaction records decision kind `withdrawn_without_replacement`, clears the consumer-visible current projection through an explicit no-winner tombstone, and permits nullable replacement identity only for that decision kind. The withdrawn current blob is then a single-predecessor deletion/recovery flow: reserve a pair id, back up the predecessor, persist immutable `manifest_kind=withdrawal_tombstone` with decision/outbox key and file watermark, create a no-winner catalog snapshot containing it, append the verified pair closure, and only then convert the recovery pin and unlink. No replacement blob is fabricated. Until those gates pass, bytes may remain physically pinned but are not locally effective or streamable through the public asset route.

Alternative: retain every physical revision. Rejected because the user explicitly requires one most-effective attachment per instrument/fiscal year. The trade-off is that version 1 cannot locally replay a pre-correction PDF.

Alternative: delete original as soon as correction metadata appears. Rejected because an incomplete or corrupt replacement would leave no usable report.

### Make local-first ensure the only consumer acquisition path

`ensure_annual_report()` accepts instrument/fiscal year or exact source filing identity, an `allow_network` flag, wait/queue policy, and integrity level.

```text
verified local effective asset -> return local hit
metadata only                  -> acquire attachment
no matching metadata          -> bounded instrument discovery -> acquire
ambiguous candidates           -> fail closed
storage/network disabled       -> explicit blocked/missing
```

Internal batch consumers may wait within configured bounds. API calls that need asynchronous acquisition create or reuse a durable operation and return the caller's opaque `asset_request_id` subscription handle; an immediate local hit or explicit network-disabled local miss returns without a subscription rather than blocking indefinitely or exposing the internal operation id.

Exact identity prevents legal-filing substitution, but it does not override version 1 retention. A known superseded or withdrawn predecessor whose bytes were deleted returns its metadata and explicit local-content-unavailable state; ordinary consumer/API ensure cannot redownload it. Restoring historical predecessor bytes would require a separately authorized future operator policy, because allowing routine exact-filing acquisition would defeat the one-effective-attachment rule.

An exact-filing selector may additionally pin an attachment id plus expected content hash or observation version. A pin must match that immutable observation; an unpinned request means the current observation of that legal filing. Every attachment/withdrawal observation carries `version_available_at`, preferring an official effective time and otherwise using `first_observed_at`, so knowledge-cutoff queries cannot see bytes or withdrawal state that appeared after the cutoff merely because the parent announcement was older. When the exact source-qualified filing is absent from the local catalog and network use is authorized, the service first uses a provider-supported exact-id lookup or a bounded source/instrument/category/date discovery scope capable of proving that exact identity. It may register other records returned by the bounded query as metadata evidence, but it cannot substitute a same-period or newer filing for the requested legal identity. A complete no-match returns an explicit exact-filing metadata miss; provider-incomplete evidence remains retryable or blocked.

### Use latest-only full-market bootstrap with targeted completeness repair

In version 1, “full A-share market” means the complete set of still-listed RMB-denominated A-share stocks at the snapshot cutoff, not every historically delisted security. The versioned eligibility policy covers SSE, SZSE, and BSE, including main-board, STAR Market, ChiNext, BSE, ST, and temporarily suspended-but-not-delisted stocks; it excludes B shares, funds/ETFs, bonds, indices, and other non-A-share security types. Inactive/delisted instruments remain available through bounded explicit ensure by a caller with the required acquire scope, but are not part of the default bootstrap and never create scheduled denominator/cursor scope or a historical delisted-universe scan.

A local instrument master cannot prove that a security row is wholly absent. Each production bootstrap and universe refresh therefore pairs the local master snapshot with an independent auditable listed-security census, such as official exchange security lists or an approved equivalent. The census retains source/exchange, query boundary, completeness watermark/version, acquisition time, and raw-content hash. Every effective coverage snapshot references its paired census snapshot id; a local-master-only snapshot may support bounded work but cannot prove full-market completion. A census-only security, identity mismatch, missing eligibility field, stale/incomplete census, or missing target exchange becomes explicit `eligibility_indeterminate` evidence and prevents a full-market completion claim. The daily workflow refreshes or revalidates the pair before each run under a versioned cadence and persists attempted/effective refresh times. The last acceptable paired snapshot is retained when either side refreshes incompletely, but an expired pair cannot claim completion. Snapshot identity, eligibility/census policy versions, master-data and census versions, freshness, and reconciliation differences are persisted.

Bootstrap phases:

1. snapshot the target universe and listing metadata;
2. adopt and classify existing valid local annual-report files;
3. scan annual-report categories market-wide through bounded date partitions covering current and prior filing seasons;
4. select each instrument's latest available fiscal year and correction winner;
5. publish, persistently retain, and count only winners; when trusted hash/precedence evidence is absent, a versioned bounded policy may temporarily read competing candidate bytes, persist immutable hash/length/retrieval/cleanup evidence, and discard or quarantine non-winner temporary bytes without creating a canonical blob;
6. create a rotating targeted repair queue for uncovered instruments;
7. search each missing instrument backwards through bounded annual-category windows until a valid latest report is found or listing/coverage bounds prove empty;
8. finish successfully only when every target has complete discovery evidence and `bootstrap_asset_status=available`, has unexpired `bootstrap_asset_status=confirmed_missing`, or has a completely proven `overdue_missing` expected period alongside an older available asset under the default policy; any incomplete, retryable, or blocked scope makes the run partial or blocked.

Market-wide discovery prevents a normal one-request-per-stock strategy. Targeted scanning is reserved for the shrinking missing cohort. The run fixes `as_of`, one inclusive evidence-visibility cutoff derived in project timezone, source/query fingerprint, expected fiscal-year and listing/search bounds. Market scans, targeted repair, retries, resume, candidate classification, observation selection, and winner activation all reuse that persisted cutoff and fingerprint. A candidate is bootstrap-visible only when its normalized publication evidence and selected observation `version_available_at` are at or before the cutoff; a later announcement, attachment observation, silent update, or withdrawal belongs to daily maintenance even if it is encountered before bootstrap finishes. A versioned fiscal-year policy derives the candidate upper year, disclosure-due year, and earliest searchable year from `as_of`, project timezone, fiscal-year end, listing date, configured disclosure-calendar boundary, provider coverage start, and bounded lookback. Version 1 defaults calendar-year A-share reports to an April 30 deadline in the following year; any market-calendar override changes the policy fingerprint. Candidate years are searched newest first. A completely empty not-yet-due year may allow the newest actually published older report to remain the latest available report, but an incomplete newer-year scope cannot. Per-instrument bootstrap coverage uses the distinct field `bootstrap_asset_status=available|confirmed_missing|retryable|blocked`; this is not the front-facing byte-state field `asset_availability=local_valid|metadata_only|missing|ambiguous|corrupt|superseded|blocked`. `bootstrap_asset_status` is recorded separately from expected-period coverage (`not_due|current|overdue_missing|incomplete`), and every row also records latest winner fiscal year plus terminal/retry evidence. Once a report is due, complete absence becomes `overdue_missing` even when an older report is locally available. By default this degrades readiness and remains in repair but does not block daily enablement, because daily discovery is the mechanism that must detect a delayed filing; a versioned deployment policy may make it a stricter blocker. `confirmed_missing` requires complete successful coverage across the eligible search range, listing/source-bound evidence, and an expiry. A discovered but unverifiable latest correction blocks final coverage or leaves an already-serving predecessor explicitly provisional without `available|current` latest-only coverage credit.

A `confirmed_missing` terminal record is an evidence bundle rather than a boolean. It retains every required source/route scope, each successful-empty query boundary and watermark, listing evidence, bootstrap `as_of`/cutoff, confirmation/expiry times, route/query/classifier/eligibility fingerprints, and stable source/checkpoint/route-equivalence references. Missing, expired, or fingerprint-incompatible evidence cannot be restored as terminal missing and returns the instrument to bounded repair.

### Use cursor-driven daily windows with adaptive date partitioning

Daily state is keyed by source, exchange, normalized `annual_report` category, market scope, and query-policy fingerprint. It keeps provider item position separate from a range-coverage watermark and persists a monotonic state version plus lease generation. The normal start is committed `covered_until` minus a configurable overlap, defaulting to three calendar days, and the end is one fixed run cutoff. A provider item/page cursor is reusable only to resume the same incomplete query fingerprint, fixed cutoff, and parent window; a new overlap window starts from its date range unless the provider contract proves that carrying the cursor cannot truncate overlap. Cursor, gap, and `covered_until` commits use compare-and-swap against the expected state version, lease generation, query fingerprint, parent window, and fixed cutoff. A stale worker may persist idempotent discovered metadata, but cannot move `covered_until` backwards, overwrite a newer cursor or gap, or change a newer parent's completion state. A fully successful window advances `covered_until` to its fixed end even when it contains no eligible records or only records older than the end; item timestamps alone never define completed time coverage.

If a window exceeds provider bounds, selected metadata is retained and the interval is bisected. A single dense day continues through durable page ranges or provider-supported subscopes under the fixed cutoff; its parent completes only when every child completes, otherwise it remains an explicit blocker. The boundary fixture uses exactly 1,500 distinct announcement ids with a provider cap of 600 records per page or continuation and requires exactly 1,500 unique registrations before the parent cursor advances. Internal coverage uses timezone-aware timestamps, while each provider adapter converts to the provider's declared parameter precision, such as project-timezone `YYYY-MM-DD` for date-only endpoints, and applies explicit boundary re-filtering; internal ISO datetimes are never passed blindly to date-only APIs. Discovery coverage advancement occurs only after the full metadata window completes successfully. Attachment failure after metadata completion does not roll back the discovery coverage watermark; it creates a separate retryable attachment operation. Rediscovering the same attachment observation updates observation evidence but does not reset completed, not-yet-due, exhausted, blocked, or operator-held acquisition state; only a new observation, due retry, or audited repair reopens work. Primary and fallback sources keep independent item and coverage cursors. A complete fallback advances only its own source-qualified cursor and never advances or erases a failed primary cursor/gap. When the versioned route policy explicitly proves query equivalence, that fallback may satisfy a separate route-level required-coverage projection used by confirmed-missing/readiness; otherwise the route-level projection remains incomplete. Every source gap remains auditable.

After market discovery, one bounded rotating cohort repairs instruments missing the expected latest annual report. Reconciliation has two bounded layers: a longer publication-window scan and an oldest-first period-level queue over every managed `instrument + fiscal_year`. The latter persists `last_reconciled_at`, retry/checkpoint state, and a maximum cycle so failures do not silently advance an item and old fiscal years cannot starve; it can discover a correction first indexed years after its nominal publication window. The provider capability matrix declares whether ETag, Last-Modified, official version/hash, or another source signal can prove that managed attachment bytes are unchanged. Where no trustworthy signal exists, a versioned bounded cadence performs conditional retrieval or temporary content-hash verification under the normal request, byte, reservation, rate, and mount gates. Changed bytes under the same legal attachment identity create a new immutable observation and trigger period reselection; unchanged bytes create neither a new canonical blob nor a change event. A route that cannot support bounded verification exposes a source limitation and cannot claim silent-update completeness. Withdrawal-only metadata triggers period-scoped transactional reselection even when no attachment is eligible for acquisition. If one batch contains an original and a legally later complete correction, the correction is the only final winner candidate; an unverifiable correction blocks bootstrap, while an already-serving legal original may remain explicitly provisional without latest-only coverage credit. Before each daily run, the active-universe pair is refreshed or revalidated under its versioned cadence so new listings enter repair and delistings leave the denominator without deleting files. The daily run reports metadata discovery, late-revision reconciliation, silent-update verification, and attachment readiness separately.

Bootstrap-to-daily handoff persists the bootstrap cutoff, query fingerprint, and only those per-source coverage watermarks whose equivalent daily discovery scopes completed through that cutoff. Once readiness gates pass, daily discovery starts from each valid handoff watermark minus overlap. Any scope without compatible complete coverage uses the configured bounded initial filing-season window, so enabling daily mode creates neither an unbounded rescan nor a gap between bootstrap and daily maintenance.

Alternative: fixed multi-year daily scan. Rejected because it repeats high-volume historical pages.

Alternative: query all instruments daily. Rejected because roughly 5,500 active stocks would create unnecessary identity and negative-result traffic.

### Provide hybrid download policy

The independent daily job proactively downloads the selected effective complete original or complete correction in version 1, as explicitly required. Competing non-winners and notice-only corrections remain metadata/evidence unless bounded candidate verification is required; the architecture still separates metadata and attachment stages so future announcement types can use metadata-only or lazy policies.

On-demand ensure remains a correctness fallback for missed, manually requested, or historical assets. A scheduler run is an optimization and coverage mechanism, not a prerequisite for business use.

### Adopt current files before creating the canonical root

Migration inventories versioned configured legacy annual-report roots, which by default and contract include the business-profile and broker roots, and validates source identity, instrument, report period, PDF signature, content length, and SHA-256. Valid current winners are registered without network download. Unknown `data/filings` directories may be reported read-only as out of scope, but are never recursively adopted or cleaned without an explicit root and classification policy.

The default target root is a business-neutral content-addressed physical pool:

```text
data/filings/announcements/blobs/
  {content_hash_prefix}/{content_hash}.pdf
```

Instrument, fiscal-year, exchange, source, and filing identities remain database projections. During shadow migration, a canonical record may reference an existing path, including a broker-held complete original or complete correction. Shadow records remain excluded from production effective lookup, bootstrap coverage, and consumer parsing until source/period/classification/hash/effective-decision reconciliation passes. An independent asset-adoption promotion gate then makes the record production-visible for shared bootstrap and daily reuse; it does not wait for either business consumer cutover. Promotion transfers custody of that exact hash-qualified path to the shared module: legacy writers and cleaners may not mutate it, and when custody cannot be guaranteed the file must first converge by verified link/copy into a controlled canonical path. Every production read, backup, and integrity audit still verifies registered length/hash and fails the asset closed if external mutation occurs. A later verified move, hard link, or copy-verify-rename can converge storage without unnecessary network download. NFS mount identity and filesystem capabilities are probed first. Duplicate paths are deleted only through a per-file manifest/hash allowlist after each affected consumer has switched and reconciliation passes; derived files, semiannual reports, other years, and conflicts are excluded. Orphans remain fail-closed unless zero-attachment-download official metadata or audited operator evidence completely resolves source attachment, instrument, period, classification, length, and hash, after which they enter shadow rather than production state.

### Treat storage capacity and backup as rollout gates

Current observed PDFs average approximately 4.6 MiB, with P95 approximately 12.9 MiB and a measured maximum approximately 43.8 MiB, projecting roughly 24-25 GiB for one full active A-share annual-report year. The remounted filings NFS has approximately 2.1 TiB free, so capacity is sufficient, but the service must not rely on a static estimate. The rollout artifact also measures current primary/backup required-set bytes, permanent recovery bytes, temporary old-plus-new peaks, expected annual growth, and an explicit planning horizon because version 1 recovery blobs are retained without GC.

Before download, operations atomically reserve planned bytes on the target filesystem using Content-Length or a configured unknown-size budget, accounting for `.part`, quarantine, and old/new overlap. They also check free bytes, warning utilization, hard stop utilization, and absolute reserve. Metadata sync can continue after the attachment hard stop. Attachment size limits are separately configurable for annual reports because the current 50 MiB generic default is close to observed large files.

Temporary files carry operation, owner, lease generation, creation time, and planned-byte identity. Configuration defines `.part` maximum age/actual bytes, owner-generation safety grace, and fail-closed handling for missing or invalid sidecars. A restarted worker may remove or adopt a stale `.part` only after owner/heartbeat/generation reconciliation and the safety grace period. Quarantine is evidence rather than a cache: configuration defines warning and hard maximum age/actual bytes, evidence retention, and operator cleanup policy. Warning thresholds degrade readiness; hard thresholds or unverifiable ownership block new scheduled attachment writes and destructive cleanup while leaving metadata discovery and verified local reads available. Quarantine is cleaned only through an operator-authorized audited command. Releasing a byte reservation does not by itself prove that temporary or quarantine bytes were removed; the two states are reconciled separately. Every dynamic path segment is validated against a declared canonical allowlist before resolution, so hash, operation, alias, source, and enum segments cannot introduce separators, encoded traversal, control characters, or non-canonical identities.

SQLite online backup does not cover `data/filings`. Add an incremental content-addressed archive backup to a verified independent storage failure domain, copying only missing blobs, validating hashes, and pairing its file manifest watermark with a recoverable catalog database snapshot that includes the replacement transaction. A reserved pair id, immutable recovery manifest, catalog snapshot that contains that manifest, and separate append-only verified closure avoid a circular immutable-manifest update. Post-snapshot catalog/outbox/operation/lineage/audit increments required by the declared RPO are copied to an integrity-chained recovery journal in the independent failure domain; restore must replay the complete interval or prove no increment from a persisted write-freeze watermark. A missing middle increment, reordered increment, tail truncation, or payload/hash tampering blocks reopen. Legacy manifest watermarks or snapshot hints may preserve a reserved pair identity during migration but can never manufacture closure; fresh bidirectional verification and a new append-only closure are required. Independence is verified from a configured unambiguous failure-domain identity plus runtime mount source, server, export, and available filesystem identity; path names, host aliases, or labels alone are insufficient, and unverifiable independence fails closed. Existing hash-named targets are reverified rather than trusted by name. New or repaired targets use same-directory temporary files, flush, hash validation, and atomic publication; restart reconciles crashes before file publication or watermark commit without treating uncommitted bytes as protected. The current filings and PVE-Bak mounts share server `192.168.188.88`, so PVE-Bak alone cannot satisfy the deletion disaster-recovery gate; QuoteBak is currently on a different server with approximately 384 GiB free. That is sufficient for the approximately 24-25 GiB version 1 bootstrap and near-term annual increments, but not an unlimited-retention assumption. The backup target therefore has its own free-space warning, hard reserve, planned-byte preflight, temporary-file cleanup, freshness, and unprotected-byte state. Backup capacity failure degrades readiness and blocks predecessor deletion but never invalidates the local replacement. Version 1 performs no automatic backup-blob garbage collection; superseded backup blobs remain disaster-recovery-only and are not consumer-visible. A later audited retention/GC policy is required before reclaiming them. Never fall back to writing a NAS backup into the local data mount when the share is absent.

Restore enablement performs a complete presence, length, and SHA-256 reconciliation of every current-effective, retention-pinned, pending-deletion replacement/predecessor, and correction-predecessor or legacy-duplicate blob in the recovery manifest referenced by the restored catalog. Recovery-only predecessor/duplicate bytes remain in the backup required set or an isolated non-consumer-visible restore area; verification does not republish them as a second primary canonical asset. Version 1 recovery-manifest entries are immutable and remain active indefinitely; automatic retirement and backup GC are outside scope. Sampling remains useful for routine drills, but a sample cannot authorize consumer reads, writes, or destructive maintenance after recovery. Backup enumeration is driven by this catalog required set and therefore includes adopted files that still use a controlled legacy path plus predecessors retained by `planned|deleting` intents before manifest commit.

### Integrate front-facing workflows through DataManager and FastAPI

DataManager exposes shared list/get/ensure/readiness/operation methods. Existing annual-report catalog methods become read-through compatibility surfaces during migration.

Additive API resources expose:

- effective annual-report metadata and integrity for an instrument;
- asset-management readiness and coverage;
- bounded ensure operation creation and status;
- caller-scoped consumer continuation/processing status;
- controlled file streaming by asset id.

Responses expose stable asset lineage, not unrestricted local paths. All metadata and existing business-profile GETs remain zero-network. Asset availability, ensure disposition, operation status, operation stage, batch outcome, result origin, and consumer-processing state are separate. Business-profile and broker responses retain existing schemas while adding optional shared lineage. No current API must synchronously crawl the market.

Ensure accepts exactly one normalized selector: either effective-period identity or exact source-filing identity. Selector members are all-or-none, fiscal year and report period must agree when both are present, exact filing identity must belong to the path instrument, and caller-supplied URLs or paths are rejected. `wait_seconds` has a versioned default and maximum: zero returns immediately, a positive value waits only to that bound, completion inside the bound returns HTTP 200, and timeout returns HTTP 202 with the existing durable handle without cancelling or duplicating work. Local-only ensure follows authenticated read policy, while any branch that creates provider work requires acquire scope. `Idempotency-Key` is bound to principal plus normalized request fingerprint; reuse with different input is a conflict rather than a new or reused operation. HTTP outcome mapping is versioned and deterministic so normal metadata absence remains a structured `200`, unknown resources are `404`, validation is `422`, idempotency/current-state conflicts are `409`, deleted predecessors are `410`, rate limits are `429`, and temporary infrastructure blockers are `503`, with authentication and permission failures following the configured non-disclosure policy. V1 business-command reason codes are fixed to `annual_report_not_found`, `network_disabled`, `provider_unavailable`, `archive_mount_unavailable`, `storage_reserve_exceeded`, `backup_gate_blocked`, `domain_scope_required`, `asset_acquire_scope_required`, `candidate_ambiguous`, `effective_state_conflict`, `idempotency_conflict`, and `consumer_processing_stale`.

A generic asset ensure obtains only the shared source asset. An API business command endpoint owned by business-profile or broker risk-control is the entry point for starting domain processing. Its versioned request reuses the same selector/network/integrity/wait/cutoff/pin rules and names a registered processing profile or expected fingerprint; the server, not the caller, computes the canonical fingerprint from governed parser/configuration state. The command creates or reuses a `consumer_request_id` immediately and uses `pending_asset` while a missing asset is acquired. It enqueues exactly one consumer operation when the selector-resolved asset is locally valid and the effective-decision policy permits processing. `local_valid` proves byte integrity only: a `provisional|ambiguous` default-effective decision remains gated as `pending_correction`/stale, while an exact-observation or knowledge-cutoff request may proceed only when its evidence scope remains valid. Asset completion never implies that business-profile or broker output is already current. Consumer-request lifecycle is separate from result freshness. HTTP 200 requires a completed request and a current result bound to the observation resolved by the normalized selector, knowledge cutoff, retention policy, and processing fingerprint: default effective-period work uses the present effective asset, while exact-filing or historical work uses the pinned/cutoff-visible observation. A later observation outside a historical cutoff does not make that historically correct result stale; a default effective-period result does become stale when its effective asset changes. Only the owner or operator can query either request projection; internal asset and consumer operation ids remain operator/service details. Generic ensure never starts unrelated consumers. Asset request lifecycle (`active|cancelled|expired`) is distinct from the internal operation status. Local-hit/local-miss asset ensures return no `asset_request_id`; only asynchronous acquisition returns one. A local asset hit with parser work pending, a stale result, or an asset miss with acquisition returns HTTP 202 with `Location` and bounded `Retry-After` (the latter carries both caller-owned handles). Terminal `missing` projections return HTTP 200 without `Retry-After`; authentication/cross-owner non-disclosure is a separate 403/404 policy and creates no work. The business command `Location` points to the consumer request; the asset request URL is a body link. Cancelling one request type never implicitly cancels the other. Domain processing permission does not grant `annual_report_assets:acquire`; missing assets may be acquired only when both scopes are present.

The repository currently has rate limiting but no complete authentication middleware. Acquire, content, cancellation, repair, and operator endpoints therefore remain disabled unless a trusted identity and scoped permission boundary is configured; a zero-network redacted readiness summary may remain available under the ordinary read-only API policy. Durable SQLite operations, not FastAPI `BackgroundTasks`, are the source of truth. This project is intentionally AI/API-only: acceptance binds the backend candidate and OpenAPI version, proves authorized explicit acquire, denial before work, active-request idempotency, caller-owned `Location`/`Retry-After` polling, and safe content access. Asset projections expose `content_url` only for `asset_availability=local_valid`; all other public availability states and retained-internal-only content return `null`. No external UI repository, owner, page, or deployment is a V1 dependency, and API-client acceptance does not bypass production rollout or consumer-cutover gates.

### Publish asset-change events or watermarks for consumers

When an effective asset is added, replaced, repaired, withdrawn, or deleted, append a monotonic change event or watermark keyed by instrument/fiscal year/asset id. For activation, the event is inserted into an outbox in the same transaction as the effective decision and replacement edge; delivery happens after commit and is retryable. Each consumer keeps its own checkpoint and can replay missed events idempotently without rediscovery or redownload. A correction marks default-effective consumer runs stale and drives domain-specific reprocessing, but exact-observation and knowledge-cutoff results remain current when the event lies outside their evidence scope; the asset service does not delete or rewrite business facts itself.

Consumer dispatch is downstream of the committed asset boundary. A disabled consumer, enqueue failure, parser failure, or lagging consumer checkpoint changes only that consumer's continuation, processing state, and readiness. It cannot regress an asset discovery cursor, revoke an effective winner, rewrite the parent asset operation outcome, downgrade asset-layer readiness, or prevent another consumer from using the same verified asset.

Consumer cutover acceptance follows that ownership boundary. For business-profile, the announcement module proves shared lookup, exact asset/observation/hash binding, and zero duplicate provider/download/archive activity; business-profile parsing, semantic extraction, review, publication, and backlog completion remain downstream and do not gate announcement dependency readiness. For broker migration, a same-parser non-empty fact set with exact shared lineage is migration-current even when a desired business fact such as `net_capital` was also absent from the legacy parse; the missing fact remains an explicit domain completeness diagnostic and continues to block any DCF path that requires it.

### Make operations resumable and single-flight

Durable asset operations use scopes, checkpoints, leases, attempts, retry times, bounded errors, and separate status/stage/outcome fields. The internal operation status has no `expired` value; expiry belongs only to caller asset/consumer projections and idempotency tombstones. Globally single-flight identity uses a versioned acquisition work fingerprint over operation type, normalized selector/scope, acquisition and retention policy, provider route/capability matrix, classifier and integrity policy, relevant configuration fingerprint, and accepted work/network/storage bounds. Only semantically equivalent fingerprints share an active operation; a route, limit, integrity, or policy change cannot silently attach to incompatible in-flight work. The caller idempotency fingerprint remains a separate principal-scoped contract. That internal operation is not transferred to the first caller: API/consumer requests create principal-scoped subscriptions or opaque query handles that bind caller idempotency and expose only authorized projections of the shared work. A second principal may subscribe to the same acquisition without inheriting the first principal's idempotency key, consumer continuation, or diagnostics. Within configured retention, repeated principal/key/fingerprint requests return the same handle even after terminal/cancelled outcomes; an expired projection remains queryable as `expired`, and the old key cannot silently create new work. Files are written to `.part` on the same verified NFS mount, validated, fsynced where supported, atomically renamed, reopened, and reverified. Lease expiry permits cleanup and retry after process failure.

Version 1 cancellation detaches only the caller's asset subscription. It does not mutate the linked `consumer_request_id` or continuation; pending continuation cancellation uses the consumer-request contract. Once bounded shared acquisition work exists, it continues even after the last subscription is detached; this avoids ownership races and produces a reusable canonical asset. Cancelling an asset request does not stop already-started consumer processing, which remains governed by that consumer's own explicit stop contract.

The scheduler control plane uses these durable operations for authenticated manual start, status, cooperative stop, resume, and duplicate-start reuse. It retains bounded run history and exposes last successful cutoff, heartbeat age, consecutive failures, cursor lag, and oldest retry age. Front-facing readiness is a redacted summary; provider, filesystem, actor, and failure diagnostics require operator scope.

Readiness also projects the current missing-attachment count and estimated acquisition bytes with estimate basis, `as_of`, and configuration fingerprint. Known content lengths, unknown-length reservations, temporary publication overhead, and old-plus-new replacement peak bytes remain separate components; an unsafe or incomplete estimate is explicitly indeterminate rather than silently reported as zero.

## Risks / Trade-offs

- [Deleting predecessor PDFs weakens historical reproducibility] -> Preserve complete metadata, hashes, replacement/deletion audit, and explicitly scope version 1 to latest-effective local assets; require a later policy change before point-in-time source replay is claimed.
- [A correction notice is mistaken for a complete replacement] -> Require a complete full-report classification and validated PDF attachment before winner promotion.
- [Provider categories omit a report] -> Combine category-filtered market scans with bounded targeted repair of missing expected instruments.
- [A dense filing date exceeds page bounds] -> Persist completed metadata, continue stable page ranges/subscopes under a fixed cutoff, and advance the parent cursor only after all children complete; otherwise expose an unsplittable-day blocker.
- [Attachment failure is mistaken for discovery failure] -> Keep discovery cursor and attachment retry state separate; only incomplete metadata work retains the cursor.
- [Successful empty windows never move beyond the last announcement timestamp] -> Persist a separate range `covered_until` and advance it to the fixed cutoff for every complete window, including empty windows.
- [Fallback success hides an incomplete required source] -> Keep per-source cursors and gaps and let only an explicit versioned route policy declare equivalent substitution.
- [Late or backdated corrections are missed] -> Add a rotating long-lookback reconciliation cohort over already-covered assets, separate from the three-day low-latency overlap.
- [Old managed periods starve in bounded reconciliation] -> Persist per-period reconciliation age and retry state and schedule oldest-first against a configured maximum cycle.
- [Incomplete newest-year evidence is mistaken for an older latest year] -> Fix `as_of` and fiscal-year/search bounds, classify incomplete/blocked separately from confirmed missing, and never downgrade silently.
- [Bootstrap and daily maintenance leave a discovery gap] -> Adopt only compatible complete bootstrap coverage watermarks and start daily with overlap; use bounded initial lookback for every other scope.
- [Cross-source or withdrawn corrections select the wrong winner] -> Require attachment-level classification, governed mirror/legal precedence, withdrawal observations, and fail-closed ambiguity/provisional states.
- [Concurrent callers duplicate downloads] -> Use attachment-scoped leases, unique constraints, content-addressed blobs, and atomic writes.
- [Migration deletes a valid existing file] -> Adopt read-only first, reconcile manifests/hash/consumers, produce a per-file allowlist, switch reads, verify independent-failure-domain backup, and only then delete explicitly managed duplicates; never clean mixed directories.
- [Storage fills during filing season] -> Estimate planned bytes, enforce warning/stop thresholds and absolute reserve, stop attachment prefetch while continuing metadata.
- [NAS is unavailable] -> Keep local service operational, fail backup explicitly, expose readiness degradation, and prevent unsafe local fallback. Same-server exports do not count as independent disaster recovery.
- [Backup target fills as missing-only blobs accumulate] -> Enforce target-side warning/reserve/preflight, leave local assets valid, block destructive readiness, and defer backup-blob GC to a separately approved policy.
- [SQLite and NFS deletion are not one transaction] -> Persist deletion intent before unlink, finalize `deleted|failed` afterward, and run an idempotent reconciler with crash-injection tests.
- [Business parser status corrupts shared asset status] -> Separate asset and consumer-processing stores.
- [History reads use a post-cutoff correction or deleted predecessor] -> Apply knowledge-cutoff filtering and return metadata-only unavailable state when eligible predecessor bytes are no longer retained.
- [API-triggered acquisition causes unbounded work] -> Require authorization, bounded single-instrument scopes, durable asynchronous operations, rate limits, and no caller-supplied paths.
- [Active business-profile changes overlap migration files] -> Land shared contracts/storage/service first, use adapters, and migrate business-profile in a bounded later step after rebasing current work.

## Version 1 Scope Assumptions And Deferred Decisions

- Version 1 defines “full market” as the independently reconciled, snapshot-time still-listed RMB-denominated A-share universe on SSE, SZSE, and BSE; B shares, depositary receipts/CDRs, and non-stock security types are excluded, while inactive and delisted instruments remain on-demand only. Because “all stocks” could otherwise be read as including historically delisted securities, release acceptance requires explicit product sign-off for this interpretation. Expanding bootstrap to all historical delisted stocks requires a separate scope decision.
- Version 1 intentionally unlinks superseded physical annual-report PDFs from the primary consumer-visible archive after safe replacement while retaining governed non-consumer-visible disaster-recovery bytes. This is not secure erasure from every storage medium. Release acceptance requires explicit product and operations sign-off; a later requirement is needed if point-in-time reconstruction through normal source access or complete byte destruction becomes mandatory.
- Semiannual reports reuse the architecture but are not enabled in the first scheduled rollout.
