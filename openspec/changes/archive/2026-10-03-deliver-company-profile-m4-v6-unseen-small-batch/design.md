## Context

`freeze_m4_next_batch_plan` 在调用方没有传入 `delivered_ids` 时，只收集当前处理身份下已有运行记录的公司。v3 交付过 `600007.SH` 和 `600010.SH`，v4 到 v6 又反复使用 `600008.SH` 和 `600019.SH`。更早的复核还用过 `600000.SH`、`302132.SZ`、`600004.SH` 和 `600006.SH`。v6 身份自己的记录盖不住前几轮。

## Goals / Non-Goals

**Goals:**

- 这次冻结显式排除上述已观察公司。
- 计划重复读取字节一致，两家都是未见样本，且一服务、一制造。
- 运行、查询、导出使用完整 v6 身份和独立目录。第二家沿用合并观察后的剩余预算。
- 复核从这两份新年报逐条记分。失败保持失败。

**Non-Goals:**

- 不改同身份默认排除。
- 不 enqueue 在冻结任务里。
- 不预填上一轮 14/14、16/16。
- 不授权生产，不声明规模质量。
- 不做行业包、六章包、商品目录扩充或框架整理。
- 本轮未通过前不安排下一组小批次。

## Decisions

1. 已观察集合是 `302132.SZ`、`600000.SH`、`600004.SH`、`600006.SH`、`600007.SH`、`600008.SH`、`600010.SH`、`600019.SH`。冻结调用传入这个集合。
2. 新目录是 `reports/m4_v6_unseen_small_batch`。处理身份是默认身份加上 `revenue_sentence_repair=v6`。
3. 运行顺序按计划中的服务公司、制造公司。查询和导出选择同一身份。
4. 召回清单在看到交付之后建立。准确率按实际交付逐条核对。

## Risks / Trade-offs

- [漏掉某轮用过的公司] → 集合来自各轮 plan、live run 和 source review，不只来自 v6 运行记录。
- [第二家仍按满额 50000 计] → 现有 gate 会在冻结计划上把预算改成剩余额度。

## Migration Plan

先冻结并核对计划，再运行和复核。失败不回滚已有观察。
