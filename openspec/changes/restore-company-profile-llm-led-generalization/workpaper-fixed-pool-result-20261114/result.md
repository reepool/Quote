## 根因与最小纠正

原TaskService构造时把传入provider保存到runtime的 `_report_provider`，底稿正文使用它。临时脚本先以 `provider=None` 构造服务，后赋 `service.provider` 和 `service.runtime.provider`，没有改到该实际引用。注册provider检测因此拒绝，模型请求未发出。四份失败不能算模型失败或语义输出质量失败，更不能因无消费就退款式恢复已占入口。

[零调用构造诊断](wiring-diagnosis.json)及[其源码](wiring-check-snapshot.txt)已经复现原错，并验证通过公开构造参数 `provider=provider` 创建TaskService会将同一实例交到正文运行器；缺真实授权/预算时仍在client前拒绝。诊断27.743秒，不调用 `execute('run')`、不创建尝试标记、client调用0。这只证明构造接线，不冒充正常整家公司闭环或新模型成功。现有业务代码无需为该操作脚本错误修改。

下一次若另获明确授权，最小修改仅在源/库准备后、构造TaskService前创建实际client/provider，正确传入provider；业务时钟开始后把同一预算挂到原client/service/runtime，再核正文持有同一provider后才占新入口。沿用原业务源码/60项源参考和已有有效测试，不新增框架、不扩供应链或再做逐字段修补。当前整组已经结束，不能借剩余额度自动跑余8家或重开4家；新整组是否重开由用户裁决。
