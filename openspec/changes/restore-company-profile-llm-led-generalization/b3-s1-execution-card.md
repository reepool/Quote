## 3. 实现、自主范围和执行顺序

1. **先清理再开发。** 记录Git基线；按项目AGENTS§2.3—2.4核活跃进程、引用、hash和可恢复性，先持久必要故障/回执再清已结束无依赖的测试库、重复缓存/导出及失败临时副本。正式PDF、首次结果、当前安全稿、仍需接续的真实检查和并行/未知归属内容保护。统一`source scripts/quote_dev_env.sh`，临时只用`data/QuoteBak`；交接简记释放空间及必要保留用途/清理时点，不建清理台账。
2. **只改直接阻塞业务的共性问题。** 沿`company_profile_common_core`→`operations.py`→现有runtime/provider/repository/read service，公共LLM网关及唯一writer不变。保全文无候选读源、跨章业务组成稿、真实核验、成功即时保存和有效回执接续。重点是主业务/收入/投入/角色共同优先，不再把每条附注、子公司注册范围或重复条件逐条成稿核验。实际缺口由有原文的语义判断决定，不用公司/页码特例、词语门禁或同维度存在冒充覆盖。

   **本卡还必须验证正常公司的语义收束。** 现有公司可读但全部完整标志false，不能到S1仍只靠A事后数句子判断完工。在现有源发现/覆盖核验中，由真实语义阅读归并公司主要业务清单、说明核心与补充的取舍，再对最终有效主张核覆盖；附注明细留补充缺口，主要漏项继续阻挡核心。不要求每个原始major条件生成一句，也不能用程序批量降级或A的评分手填true。直接证明“核心齐全且补充有缺口能正常收束”以及“同维度另一主业漏答仍不完整”；真实S1逐家记录程序判定与独立内容验收是否一致，仍不一致如实列业务自动收束未过，不造新评分器。此项服务自动交付P0，不是先做吞吐或架构优化。
3. **最小直接证明后冻结。** 复用有效同快照回执，必要验证真实入口的持久JSON加载、非空三视图、主要业务漏项不假完整、后置否定不复活、后包失败保前包和真实发送字节/非空核验目标。若路径未改，不再跑整本mock。完成直接P0—P3/现实P4、必要Review和冻结即可真实运行，不先建设完整性/调度/预算平台。
4. **连续完成首发。** 12家首发使用一个冻结代码/模型池/prompt/预处理版本，逐家顺序运行，现池同一时刻一家语义任务。首发不得复用B2/S1旧语义答案、条件或检查，只可复用解析缓存；成功源响应及已核组即时落盘。公司达核心目标后不再扩写补充条件；全部可读范围仍须获得无候选读源机会或保具体限制，不能因已有答案将未读写为未披露。
5. **有界统一补救。** 首次失败保原结果；全部首发后最多两次共性修复迭代，先局部闭环，再以一个最终快照做每家至多一次正式后继。未变且合法的实际源/检查可在显式版本兼容链中复用；仅PDF相同、旧review_state或尾部汇总不能代替依据。影响源语义的政策/prompt变化须重验相应范围，不能拼不同版本最好结果。最终全组回归优先用已有证据直接读回/受影响路径，不为修接续把正确事实全量付费重核。

B在本卡内自主完成实现、局部修复、直接验证、冻结、授权真实运行与交接，不逐函数/逐公司请批。非阻塞风格、架构、全量附注明细及行业增强后置。当前主线是12家真实答案；不为吞吐优化开独立平台或再次给开发4家扩大收口范围。
