## 1. 唯一交付与主线取舍

在原`bounded_entry → CompanyProfileTaskService.execute("run") → 公共网关 → 原writer/read service`内，使一个覆盖全部主要业务问题的公司核心包能够成稿、完成有效支持/条件覆盖并持久读回；同一实现遇到不可修复响应或耗尽恢复时正确停止、保留合法部分。只交一项字段修复、一次请求发出或更多诊断日志不算完成。

§223真实回执表明，正文已含主营、产品、采购、自主生产及期间总额证据，但没有任何有效核验覆盖。优先修复把这些源转成可信答案的直接链，不再改预留算法、细修c3单句、优化建表、补普通产销量/排名/地区或新建通用重试/校验平台。保留源先行、主要条件、必要未读和质量底线；不以降级主要条件或放宽完整性取得true。

## 2. 先核现有失败，一次选定最小修法

只用[本次权威回执](company-core-observation-600103-20261108-receipts/)、正式解析、当前直接调用链及已有相关测试：

- 逐笔对齐13次发送与1次拒发的目的、输入/目标、输出上限、finish、usage和逻辑父请求。明确第3/4次成稿同请求失败、第7次核验2000输出截断、第2/8次成功源审重复及拒发后第12/13次发送的关系；恢复不能只按失败条数解释。
- 现有材料仅给出`schema validation failed at $ (required)`及正文哈希，未能指明缺哪个字段。先查现存必要回执；确无失败正文或精确字段路径就如实写不可恢复，不为找回它重新外呼，不把人工构造失败称为原始响应。直接复现可用明确标识的等价缺字段/截断输入。
- 在原请求构造、wire/schema及消费者中做最小协议修正。确定性版本/请求身份可以在明确的线协议中本地绑定；若改变协议，schema、版本和直接消费者一起改。不得自动补语义答案、证据或pass，也不得默许缺字段、猜原文、把reasoning当答案。不扩成全池协议改造。
- 核验目标和输出容量一起打包。保留全部主要目标，复用现有紧凑格式和分组；按实际非空目标检查完整响应能否容纳，必要时小组拆核或在既有允许输出范围内调整，不再把同一大组固定塞进2000后原样重试。所有重发计物理及恢复，不能拼截断JSON为通过结果。

上述调查服务于同窗实现，不另交“归因完成、下次再修”的准备轮。

## 3. 公司级推进与停止必须一起成立

首个核心包覆盖主营及其他主要板块、主要产品、收入机制/主要构成、公司期间总额、重要投入、经营角色及有据上下游。同源证据可跨视图复用，已成功的源响应按现有checkpoint复用；不因后续格式失败重读相同正文。已读总额应进入核心成稿，而不是只留在source_conditions；未解决的主要证据缺口仍阻塞完成。

核验分组成功即保存该组，失败不清前组。对可修复格式错误，在现有恢复范围内携带失败原因/原目标定向修复；没有变化的同一失败请求不机械重发。新增业务补读与失败后的恢复按真实目的区分，不能靠request_id、变页、换组或新目标身份绕过卡级限制；也不能把已成功源审的重复发送当作无成本新业务。

本卡明确未来行为：首次发生卡级恢复耗尽拒发后，本次入口不再发任何模型请求，执行本地保存/查询/导出后结束。正常首发、修复和必要业务补读的计数边界在现有代码中一致落实；不扩大恢复次数、不把拒发伪装为真实超时。原§223发生的后续发送及账本如实保留，不追改为已经及时停止。
