# Quote 项目开发与架构治理总纲

> 状态：长期有效
>
> 适用对象：人工开发者、Codex、Claude、Gemini 及其他参与本仓库开发的 AI 代理
>
> 目标：所有功能围绕清晰业务所有权演进，保持生产稳定、实现路径单一、代码复用有据、历史实现及时退出

## 1. 总体原则

Quote 采用边界清晰的模块化单体架构。项目允许多个使用入口、多个业务数据域和多个独立数据库，但不允许同一业务动作存在多套互不等价的生产实现。

所有开发遵循以下顺序：

1. 明确业务目标、输入、输出和验收条件；
2. 确认现行权威入口、写入 owner、数据口径和时间语义；
3. 优先复用现有应用服务、repository、provider 和配置；
4. 在同一权威执行链上完成最小充分改动；
5. 验证代表性业务路径和现实边界；
6. 删除本次变更明确替代的旧实现、临时兼容和一次性工具；
7. 更新当前文档并及时归档已完成 OpenSpec change。

不得为了快速实现局部功能而在 CLI、API、scheduler、Telegram、脚本或新模块中复制现有业务循环。

## 2. 权威执行链

### 2.1 多入口、单实现

允许的外部入口：

- CLI；
- FastAPI；
- Scheduler；
- Telegram；
- 明确标记的 operator script。

这些入口只负责参数解析、鉴权、任务提交和结果展示，必须汇聚到同一个 application command/query。

```text
CLI / API / Scheduler / Telegram / Operator Script
                         |
                         v
             Application Command / Query
                         |
              Domain Service / Read Service
                         |
               Repository / Provider Port
```

外部入口不得：

- 直接复制下载、回填、对账、修复或同步循环；
- 绕过应用服务直接写业务表；
- 自行发明 universe、代码格式、交易日或失败语义；
- 通过 subprocess 启动另一套生产实现；
- 用脚本名称代替明确的业务模式合同。

### 2.2 一个写入 owner

每个业务写入动作必须有且只有一个 owner。owner 负责：

- 输入合同；
- 状态和幂等语义；
- 写入边界；
- 失败与重试语义；
- 业务报告结果；
- 相关回归测试。

增量、全量、回补、对账、dry-run 可以是不同命令，但必须明确共享哪些规则、分别拥有哪些副作用，不得靠相似函数名或 job 名隐式区分。

## 3. 模块职责

| 角色 | 应负责 | 不应负责 |
|---|---|---|
| 外部适配器 | 参数、认证、提交、展示 | 业务循环、SQL、provider fallback |
| 应用服务 | 单一用例编排、幂等和事务边界 | UI/Telegram 格式、脚本环境 |
| 域服务 | 金融规则、状态机、权威选择、时间语义 | 进程启动、CLI 参数、全局容器 |
| Read service | 稳定本地查询和输出投影 | 隐式联网、生产写入 |
| Repository | 表、SQL、事务、迁移 | 调度策略、业务模式决策 |
| Provider | 上游协议和源字段语义 | canonical 写入所有权、跨域决策 |
| 共享基础设施 | 已验证相同的技术原语 | 万能 ingestion/store/provider 框架 |

依赖方向必须从入口指向应用与领域，再指向基础设施。生产模块不得反向依赖 `scripts/`、`tests/` 或 OpenSpec evidence。

## 4. 复用准入规则

新增共享抽象前必须同时满足：

1. 至少两个当前生产调用方需要相同语义；
2. 输入、输出、异常和生命周期一致；
3. 抽取后能删除真实重复代码；
4. 不要求调用方传入大量无关参数；
5. 有覆盖全部调用方的合同测试。

仅有相同类名、相似 SQL、相同 HTTP 库或未来可能复用，不足以建立共享层。

以下规则特别适用于 Quote：

- 证券标识允许多个外部别名，但进入业务层后必须归一到 canonical identity；
- 股票、期货、外汇、商品发布日历可以共享接口形状，不共享业务判断规则；
- `aiohttp`、`requests`、`httpx` 可以并存，只共享适用的代理、TLS、CA 和错误分类配置；
- API 限流、数据源 pacing、LLM RPM 不因名称相似而合并算法；
- 独立 SQLite 数据库保持隔离，只抽取已经证明相同的连接策略；
- provider 的源协议逻辑不得进入研究计算和业务编排。

## 5. 核心文件增长约束

以下文件当前是兼容门面或集中实现，在完成框架改造前不得继续承载新的大段业务逻辑：

- `data_manager.py`；
- `research/storage.py`；
- `scheduler/tasks.py`；
- `api/routes.py`。

允许的修改：

- 修复当前业务错误；
- 保持兼容所需的薄转发；
- 迁移逻辑后的删除；
- 当前在途 change 无法避开的局部改动。

新增功能应进入所属域的应用服务、repository、provider 或路由模块。以下数值是 Review 触发线，不是机械拆分目标：

- facade 方法超过 30 行；
- 普通业务方法超过 100 行；
- 单类超过 50 个直接方法；
- 单文件超过 1,500 行且继续增长。

超过触发线必须说明为什么现有稳定边界无法容纳；不得通过制造大量只有一两个函数的碎片文件规避检查。

## 6. 兼容、迁移和删除

兼容层只能是单向转发，不得保留第二套逻辑。每个兼容入口必须记录：

- 替代入口；
- 当前调用方；
- 移除条件；
- 最晚清理阶段。

代码和脚本采用以下生命周期：

| 状态 | 处理要求 |
|---|---|
| `production` | 明确 owner、入口和测试 |
| `operator` | 调用权威服务，有运行说明 |
| `migration` | 绑定 OpenSpec task 和删除条件 |
| `compatibility` | 只转发，有调用方迁移清单 |
| `obsolete` | 直接删除，Git 历史作为归档 |

不得长期建立 `legacy/` 垃圾目录。一次性迁移完成后应删除实现；仍用于生产恢复的工具必须转为明确的 operator runbook。

## 7. 生产稳定性

框架改造不得影响日常数据采集、维护和查询。每个重构 change 必须遵守：

1. 默认不改变 job id、启用状态、调度时间和生产参数；
2. 默认不改变公共 API、CLI、Telegram 命令和配置格式；
3. 默认不改变数据库路径、表结构、canonical key 和数据口径；
4. 结构迁移先保留薄兼容，再迁调用方，最后删除旧入口；
5. 写入路径迁移必须使用临时数据库或受控 fixture 验证，不对生产库做试验性写入；
6. 同一写入能力不得在迁移期双写，除非 change 明确规定且有对账、停用和回滚条件；
7. 每个切片必须能独立回滚到上一条已验证的权威链；
8. 涉及交易日、复权、可得日、生命周期或回测时点时，必须验证金融语义未改变。

若生产任务当前正在运行或工作区存在相关在途改动，重构应避开同一模块，或等当前 change 完成后再开始。

### 7.1 移动目标协议

框架改造跨越多个发布周期时，业务开发不会被冻结。已完成迁移的域，其新增功能必须直接进入新的应用服务、repository 或 adapter；不得因为旧门面仍存在而继续向旧文件添加业务实现。确需修改旧门面的，仅允许薄兼容、当前错误修复或尚未迁移调用方所需的最小适配，并须登记到对应 change 的迁移清单、替代入口和删除条件中。

“核心大文件新增业务行数为零”是默认门槛，但允许经过登记的例外。例外必须说明业务原因、影响行数、替代迁移目标和最晚清理阶段，并在该 change 验收时重新核销；未登记的增长视为阻塞问题。

## 8. 文档治理

文档分为四类：

| 类型 | 权威内容 | 生命周期 |
|---|---|---|
| `current` | 当前架构、接口、配置和模块边界 | 必须随代码更新 |
| `runbook` | 当前可执行运维步骤 | 命令失效即更新或删除 |
| `requirements` | 尚未完成或持续有效的业务要求 | 完成后进入 OpenSpec/spec 或 current 文档 |
| `historical` | 调研、回执、迁移记录、基线 | 默认由 Git/OpenSpec archive 保存，不留在当前文档入口 |

规则：

- `docs/README.md` 是当前文档唯一总索引；
- 同一功能只保留一份 current 文档和必要 runbook；
- 已完成 change 的需求稿不得继续冒充当前设计；
- 一次性回执、调查和迁移记录在内容已吸收后删除；
- 不创建“旧版”“legacy”“backup”文档目录长期堆积；
- 删除前确认有效规则已经进入 current 文档或 OpenSpec spec；
- 文档中的任务、端点和数据库清单优先由代码或配置生成。

## 9. OpenSpec 与框架改造

框架改造以 `docs/development/framework_refactoring_program.md` 为总需求和进度索引。每个 change 必须：

- 绑定一个 program requirement ID；
- 只处理一个稳定业务或架构边界；
- 列出生产不变量、依赖 change 和非目标；
- 形成可运行的纵向切片，而不是只新增抽象；
- 明确被删除的重复实现或减少的核心职责；
- 通过业务等价、调用链和生产兼容验收；
- 完成后立即归档，并更新 program 状态。

不得创建没有总纲映射的“顺手重构” change，也不得因为 Review 建议无限派生新 change。

## 10. AI 开发前检查

任何 AI 在开始功能或重构前必须回答：

1. 当前业务动作的权威 owner 是谁？
2. 是否已有可复用服务或 repository？
3. 是否会新增第二条执行路径？
4. 是否会向四个受控大文件继续加入业务逻辑？
5. 是否改变生产调度、API、配置、数据库或金融语义？
6. 是否产生临时脚本、兼容入口或文档，何时删除？
7. 当前工作是否直接推进明确验收条件？

无法回答时先调查，不开始编码。

## 11. 完成定义

功能或重构完成必须同时满足：

- 明确业务行为保持或达到需求；
- 所有入口汇聚到权威执行链；
- 当前改动没有遗留第二套实现；
- 必要兼容有明确删除条件；
- 相关测试、代表性验证和金融语义检查通过；
- current 文档已更新，历史文档已删除或从当前索引移除；
- OpenSpec tasks、program 状态、提交和推送形成闭环。

满足以上条件后结束，不继续为了抽象完整性扩大范围。
