# 上市公司画像产品与分行业语义总需求

> 文档类型：requirements（唯一权威总需求）
> 状态：阶段 0/1 已完成并审核冻结
> 生效日期：2026-09-02
> 适用市场：第一阶段为 A 股（SSE、SZSE、BSE）
> 对应 OpenSpec：`define-company-profile-product-and-industry-contracts`

## 0. 文档权威关系

本文件是公司画像产品定位、行业差异、数据结构、数据需求、来源规则、LLM 语义合同和实施分期的唯一权威总需求。后续 OpenSpec、行业需求文档、prompt、schema、代码和测试必须从本文件派生，不得各自重新定义业务含义。

以下文件自本文件生效后只作为历史实现背景，不再作为新画像语义开发的验收依据：

- `company_business_profile_and_commodity_exposure_requirements.md`；
- `llm_assisted_business_profile_and_supply_chain_requirements.md`；
- `business_profile_llm_benchmark_requirements.md`；
- `business_profile_semantic_production_runbook.md` 中关于旧语义生产和 10.3 重放的说明。

旧文件中仍然有效的证据留存、双时态、候选治理、审计、幂等、失败清理和 DCF 隔离原则，由本文件重新确认后继续有效。旧字段、旧 prompt、旧 schema 或旧任务已经实现，不代表它们仍符合新产品定义。

后续每个行业必须有独立 requirements 文档，并在本文件的“行业文档登记表”中登记状态、样本和版本。行业文档只能细化本文件，不得削弱通用安全边界；发生冲突时先修改本文件和 OpenSpec，再修改行业文档与实现。

## 1. 阶段 0：旧语义生产冻结

自 2026-09-02 起，旧公司画像语义合同停止接受新生产写入，停止继续执行旧 change 的 10.3 定向重放和后续全量回补。

冻结范围：

- 关闭 `business_profile_production_rollout`；
- 关闭手工 `business_profile_backfill`；
- 关闭旧 `semantic_production`；
- 禁止旧 `business_profile_llm_report.v2`、`business_profile_atomic_extraction.v6` 及其派生身份产生新的生产事实；
- 禁止用旧语义结果继续扩展商品暴露、供应链地位或 DCF 输入。

继续保留：

- 正式公告发现、原始年报/PDF 获取和不可变归档；
- 已有 PDF 页文本、表格制品和原始证据；
- 本地只读审计、状态查询和协作式停止；
- 为确认垃圾范围所必需、且不新增语义事实的受控清理能力。

本阶段不删除历史语义数据。旧画像事实、候选、运行记录和测试数据是否保留，不再作为新结构设计的约束；在新合同具备最小闭环后，通过独立、可审计的 reset change 物理删除旧语义结果并重建。原始正式文档和可复用原始证据不得随语义 reset 删除。

## 2. 产品定位

### 2.1 公司画像是什么

公司画像是“在给定知识时点，能够由正式披露核验的公司经营事实集合”，用于回答公司做什么、靠什么产生收入、经营规模如何、主要投入和销售关系是什么、业务结构如何变化。

它不是：

- 公司简介的自由文本摘要；
- 由行业常识拼接的百科；
- 由模型直接生成的投资结论；
- 完整财务报表的复制；
- 自动估值模型；
- 把产品、指标、上下游角色和商品敏感性混在一个“活动”字段中的松散标签集合。

### 2.2 主要用户

第一用户是需要核验经营事实的公司研究员和行业研究员。下游程序、研究报告和 DCF 只能读取已经批准、时点有效、证据完整的事实。

### 2.3 预期效果

产品必须使研究员能够：

1. 快速理解公司总体业务及主要业务板块；
2. 查看按产品、行业、地区披露的收入、成本和毛利率；
3. 对齐产品的产量、销量、库存和产能等经营指标；
4. 查找年报明确披露的原材料、客户、供应商和业务变化；
5. 区分原文事实、程序推导和研究假设；
6. 查看每条结论的报告期、披露口径、原始单位、证据页和知识可得日；
7. 识别未披露、不适用、抽取失败和口径不清，而不是把空数组误当成功；
8. 观察公司转型、并购、剥离或借壳前后的业务 regime 变化，不用当前行业覆盖历史。

## 3. 第一版冻结范围

### 3.1 第一版必须回答

第一版以“通用基础包 + 经人工批准 manifest 指定的制造/材料行业包”形成第一个业务闭环，但行业合同必须来自多家公司、多种披露形态的共性研究，任何单家公司都不能成为行业定义本身。人工指定只适用于首个受控试点；后续行业包必须通过独立研究和验收后，才可由 regime-aware resolver 自动启用。

第一版必须回答：

以下是研究员问题清单，不等于所有字段均为 `required` 完成门。每个问题在具体公司/报告中的义务级别，必须由“已启用行业包 × 当前章节任务”的检查清单声明为 `required`、`conditional`、`optional` 或 `not_applicable_by_design`。

1. 公司主要做什么：保存年报“管理层讨论与分析—主要业务”对应原文，并提取有证据的核心活动；
2. 收入、成本、毛利率如何按产品、行业或地区拆分；
3. 可与产品或业务范围对齐的产量、销量和库存；产能在实际披露时记录，是否为 required 由行业包单独声明；
4. 年报明确披露的原材料、能源、具名或匿名客户、供应商及集中度；
5. 主营业务、重大资产和经营模式是否发生变化；
6. 每条记录属于披露事实、程序推导还是研究假设；
7. 每个必需问题的覆盖状态和失败原因。

### 3.2 第一版明确不做

- 不承诺完整产业链地位或自动判定资源商、加工商、贸易商、制造商的完整组合；
- 不从“生产某产品”自动推出全部原料、客户、上下游和商品方向；
- 不自动给出商品价格敏感性、传导率、套保有效性或 DCF 参数；
- 不做跨期经营变化的自由叙事生成，只保存结构化事件和可验证差异；
- 不全量进入财务附注；附注中的合并范围、存货、套保、金融工具等属于明确扩面；
- 不同时实施金融、医药、TMT 等行业包；
- 不覆盖港股；
- 不把研究长文或 LLM 润色文本当权威事实。

### 3.3 首个纵向切片的样本原则

首个切片选择制造/材料行业的多样本集合，至少覆盖：

- 多产品与单一主业公司；
- 有产销存表和无标准产销存表的披露；
- 跨页表格、单位写在表头、单位写在脚注等形态；
- 主体为合并集团、发行人或明确子公司的情况；
- 主业稳定和发生重组/业务转型的情况；
- SSE、SZSE、BSE 的代表性报告。

首个验证集合至少包括三份年报且覆盖至少两家公司；其中一份可以作为首个重点验证报告，另外两份必须来自其他公司或其他年度，用于覆盖表头变化、合法不适用和主体口径差异。宁德时代可作为动力电池制造/材料样本之一，用于验证产品收入与产销存分离、合并口径和转化活动，但不得用其年报结构、字段或术语代表整个行业。

## 4. 事实分层与权威边界

所有输出必须标记 `assertion_class`：

| 类别 | 定义 | 允许来源 | 是否可直接进入研究事实层 |
|---|---|---|---|
| `reported_fact` | 报告直接披露的文字、数字、关系或事件 | 正式报告/公告；受限结构化聚合源 candidate | 证据和治理通过后可以 |
| `deterministic_derivation` | 由批准事实按版本化公式计算 | 程序 | 可以，但必须保留输入、公式和版本 |
| `research_assumption` | 价格方向、材料性、传导率、预测等研究判断 | 人工或独立模型 | 不得伪装为公司披露事实 |

LLM 不能把自己的理解升级为 `reported_fact`。行业常识只能帮助定位和解释，不得补写公司未披露的产品、原料、客户、角色或数字。

## 5. 总体业务说明

每个公司/报告期必须建立 `BusinessOverview`：

- 首选来源是 `business_overview` 章节家族；对于采用中国上市公司常见模板的年报，通常对应第三节“管理层讨论与分析”中的“主要业务”，但不得把该编号或标题硬编码为通用合同；
- 保存原文段落，不以摘要替代原文；
- 保存章节标题、页码、文档 ID、原文 hash、报告期、主体口径和知识可得日；
- 若年报模板章节编号不同，按标题语义和披露模板定位，不硬编码“第三节”；
- 若正式更正稿只更正部分内容，仅在更正范围内覆盖原稿，其余内容继续引用原有效报告；
- 研究视图可生成简短摘要，但摘要必须仅引用已批准原文和结构化事实，不得新增数字、角色、因果或评价。

`BusinessOverview` 负责总体概括，不承担收入、产销存、客户供应商等结构化指标。它可以为空的唯一合法原因是相应章节经完整读取后确认不适用；章节缺失、未选入、解析失败或超预算必须标记失败。

## 6. 通用信息对象

### 6.1 核心对象

| 对象 | 职责 | 禁止混入 |
|---|---|---|
| `Company` | 证券与法律主体身份 | 报告期经营结论 |
| `BusinessRegime` | 某段有效期内的主业结构和行业包组合 | 永久静态行业标签 |
| `IndustryPackageAssignment` | 报告期/regime 对应的主包、扩展包和依据 | 开发者主观选择 |
| `BusinessOverview` | 主要业务原文与受控摘要 | 表格数值和推测 |
| `Segment` | 产品、行业、地区等披露维度 | 产量/销量动作 |
| `Activity` | 公司明确从事的生产、加工、销售、服务等行为 | 收入、产量等 measurement |
| `Measurement` | 某对象、期间、口径下的单一指标 | 多个指标压在一条活动中 |
| `Relationship` | 明示客户、供应商、合作或合同关系 | 行业常识推导关系 |
| `ValueChainRole` | 由完整证据和明确规则得到的有限角色 | 完整产业链位置猜测 |
| `CommodityExposure` | 明示商品事实及其受治理映射 | 价格敏感性和 DCF 假设 |
| `BusinessEvent` | 收购、出售、借壳、重组、主业切换等事件 | 无时间边界的当前状态 |
| `Evidence` | 文档、页、表格、行、引文和 hash | 模型生成内容 |
| `CoverageResult` | 字段要求、读取范围和结果状态 | 空数组代替诊断 |

`ValueChainRole` 和 `CommodityExposure` 在第一版只保留边界与后续接口定义；阶段 4/5 不要求实现其生产 writer，验收要求是不得从活动或产品事实自动发布角色、商品方向或 DCF 结论。

### 6.2 Activity 与 Measurement 必须分离

“公司生产电池系统”是 `Activity`；“电池系统产量 100 GWh”是 `Measurement`。营业收入、营业成本、毛利率、产能、产量、销量和库存必须分别保存为独立 measurement，并通过共同的产品/分部、报告期、主体和证据关联。

不得因为一行表格包含四列就把它压成一个活动，也不得因为出现“销量”把数字写成 `sells` 活动。动作描述公司做什么；指标描述数量或金额是多少。

### 6.3 来源 occurrence 与语义内容

同一物理表格单元格或叙述引文必须有稳定来源定位；业务语义、规范化名称和模型解释单独版本化。表格 measurement 必须拆分为 `logical_slot`（如 revenue、cost、gross_margin、sales_volume）和 `physical_anchor`（行标签、列标题、页码、表格 ID、单元格或有界引文位置）。来源位置相同但 logical slot 不同的指标不得合并；physical anchor 变化时必须重新核验。

## 7. 完备性合同

完备性采用两个正交维度，避免把 `required` 与结果状态混用。完备性只针对“本次已启用行业包 × 本次章节任务”预先登记的检查清单逐项表态，不允许模型或运行时枚举全世界可能指标并批量生成 `not_disclosed`。

### 7.1 字段要求级别 `requirement_level`

- `required`：该行业包/报告形态必须检查；
- `conditional`：启用条件满足时必须检查；
- `optional`：披露则记录，不作为完成门槛；
- `not_applicable_by_design`：该行业包明确不适用。

### 7.2 抽取结果状态 `coverage_status`

- `observed`：发现并通过结构、证据和语义校验；
- `not_disclosed`：必需章节/表格已完整读取，但公司未披露该信息；
- `not_applicable`：根据行业包和报告内容确认不适用；
- `extraction_failed`：应读取但因缺页、解析、预算、schema、单位或其他问题未得到可靠结果；
- `unclear`：存在内容但主体、单位、范围或语义无法唯一确定，需修复或人工复核。

### 7.3 空结果规则

- 制造公司存在“分产品营业收入”表却返回空：`extraction_failed`，不得完成；
- 已完整读取客户章节但未披露具名客户：可为 `not_disclosed`；
- 行业包不要求产量：`not_applicable`；
- 页面超预算未送入解析：`extraction_failed`；
- 主体在发行人和合并集团之间无法判断：`unclear`。

每个 required 字段和触发条件已满足的 conditional 字段必须产生记录或 coverage status；optional 字段只有在检查清单明确要求检查且章节已读取时才可记录 `not_disclosed`。空数组没有业务含义。银行产量等未进入当前包检查清单的字段应是 `not_applicable_by_design`，不产生无意义的未披露记录。

## 8. 来源、优先级和时间语义

### 8.1 来源角色

| 来源 | 角色 |
|---|---|
| 交易所/CNInfo 正式报告和更正稿 | 公司事实权威来源 |
| 正式专项公告 | 对重大合同、产能、重组等特定事实的权威补充 |
| 东方财富、同花顺等免费聚合源 | 发现、初筛、交叉校验和 candidate，不单独裁决争议 |
| 公司官网 | 仅在可确认正式发布身份和时间时作为补充 |
| 行业资料与常识 | 行业包设计和定位辅助，不是公司事实 |

### 8.2 冲突优先级

1. 更正报告只在明确更正范围内优先于原报告；
2. 同一事实的更新公告按知识可得日和有效期形成后继，不回写历史；
3. 正式报告与聚合源冲突时，正式披露优先，聚合源保留诊断；若正式年报目标表为 `extraction_failed`，东方财富或同花顺数字只能进入交叉校验 candidate，不得晋升 approved，也不得把正式抽取失败改写为成功；
4. 表格与叙述冲突时不得默认“表格永远优先”，应比较主体、期间、维度、单位和是否为汇总/明细；不能解释则 `unclear`；
5. LLM 解释不得覆盖原始表头、单位、脚注和正式原文。

### 8.3 双时态

每条事实至少保存：

- `valid_from/valid_to`：事实适用的业务期间；
- `knowledge_from/knowledge_to`：市场或系统可获得该披露的时间；
- `report_period`、`published_at`、文档版本和 supersession lineage。

公司转型不能把新主业追溯覆盖旧年度，借壳前后的业务必须属于不同 regime。

## 9. 年报章节家族与抽取合同

上市公司年报章节编号和标题不完全一致，系统使用“章节家族 + 标题别名 + 表头签名 + 语义锚点”，不得假设所有年报结构统一。

| 章节家族 | 主要信息 | 第一版处理 |
|---|---|---|
| 主要业务/经营模式 | 总体业务、主要产品服务、模式 | 原文保存；活动可 LLM 抽取 |
| 管理层讨论与分析 | 经营回顾、业务变化、风险 | 分主题选段；不一次送整章 |
| 主营构成/分部 | 产品、行业、地区收入成本毛利率 | 表格确定性优先 |
| 产销存/产能 | 产量、销量、库存、产能、利用率 | 产量/销量/库存按行业包要求检查；产能披露则记录，复杂表头再交 LLM |
| 采购/原材料/能源 | 明示投入品、采购模式、价格变化 | 叙述/表格分别抽取 |
| 客户/供应商 | 具名关系、匿名集中度 | 严格区分关系与集中度 |
| 重大变化/重组 | 收购、出售、借壳、主业变化 | 形成事件和 regime 候选 |
| 财务附注 | 分部、合并范围、存货、套保等 | 非第一版常规面；由行业文档逐项扩面 |

每个章节家族必须独立定义：输入页范围、必带表头/脚注、可提取对象、禁止推断、coverage 门槛和失败策略。不同语义任务不得共享一个无边界大 prompt。

## 10. 确定性解析与 LLM 分工

执行顺序固定为：

1. 选择有效正式文档和章节；
2. 建立可复现页文本与表格制品；
3. 对结构稳定的表格、标题、单位和脚注做确定性提取；
4. 对确定性规则无法可靠完成的语义理解调用 LLM；
5. 程序执行 schema、证据、单位、口径、范围、重复和跨字段校验；
6. 不通过的结果进入 repair 或人工 review，不得静默完成。

适合直接解析的内容包括明确表头下的收入、成本、毛利率、产量、销量和库存，以及实际披露的产能。适合 LLM 的内容包括主要业务叙述、复杂表头归属、明确关系、业务变化和主体范围辅助判断。直接解析失败后才允许 LLM fallback，且必须携带原始表头、单位、脚注和上下文。

## 11. LLM 语义合同

### 11.1 LLM 的角色

LLM 是受控语义抽取器、修复器和验证器，不是公司画像的最终作者。程序负责文档选择、数据结构、单位换算、身份、时态、持久化、覆盖判断和发布。

### 11.2 仅允许三类请求

- `extract`：从给定章节/表格中抽取严格 schema 候选；
- `repair`：根据明确错误码和原输入修复结构或可定位字段；
- `verify`：独立核对候选是否得到输入证据支持。

`human_review_package` 是程序将候选、证据、冲突和可选项打包给人工的产物，不是第四类 LLM 请求。

### 11.3 每次请求必须提供

- 公司和报告身份，但不得提示模型用公司常识补答案；
- 报告期、文档类型、章节家族和主体候选；
- 连续的原文/表格、表头、原始单位、脚注、页码和证据锚点；
- 当前启用的行业包、字段需求清单和字段定义；
- 允许的 metric/action/relation 枚举及正反例；
- 完备性输出要求；
- 明确禁止推断的事项；
- 严格 JSON schema 与版本。

### 11.4 每条返回必须包含

- `object_type` 和稳定请求内 ID；
- 原始名称和值，不先替程序规范化；
- `metric_type`、`logical_slot`、`physical_anchor` 或 `action_type`；
- 报告期、期间类型、主体范围和披露维度；
- 原始单位、表头、脚注引用；
- 精确 evidence 引用；
- `reported_fact` 或待验证的语义类别；
- `coverage_status` 及原因码；
- 不确定时的候选选项，不得强行唯一化。

### 11.5 禁止事项

LLM 不得：

- 猜测未披露数字、单位、主体、期间或客户名称；
- 按数值大小猜 `%`、万元或小数；
- 把销量当销售额、库存当存货金额、产量当收入；
- 把同一表格行的不同 logical slot 合并；
- 根据行业或产品补齐上下游；
- 直接输出数据库 ID、approved 状态、商品价格方向或 DCF 参数；
- 用摘要替换证据；
- 在研究文字中新增结构化事实之外的数字、角色和因果。

## 12. 指标与动作字典

### 12.1 第一版指标

| `metric_type` | 业务定义 | 常见单位 | 关键要求 |
|---|---|---|---|
| `operating_revenue` | 披露口径下的营业收入 | 元/千元/万元/亿元 | 保留产品/行业/地区维度 |
| `operating_cost` | 与收入同口径营业成本 | 同上 | 不等同采购额 |
| `gross_margin` | 披露或计算毛利率 | % 或 fraction | 标记 reported/derived，程序只换算一次 |
| `capacity` | 期末或期间产能 | 行业单位 | 披露则记录，必须有期间/时点；是否 required 由行业包声明 |
| `production_volume` | 期间产量 | 行业单位 | 不等同收入 |
| `sales_volume` | 期间销量 | 行业单位 | 不等同销售额 |
| `inventory_volume` | 期末或期间库存量 | 行业单位 | 不等同资产负债表存货金额 |

第一版固定以下一一对应关系，禁止实现自行增加同义槽位：

| `metric_type`（目录语义） | `logical_slot`（身份槽位） |
|---|---|
| `operating_revenue` | `revenue` |
| `operating_cost` | `cost` |
| `gross_margin` | `gross_margin` |
| `capacity` | `capacity` |
| `production_volume` | `production_volume` |
| `sales_volume` | `sales_volume` |
| `inventory_volume` | `inventory_volume` |

`metric_type` 表示业务语义；`logical_slot` 是稳定的业务指标槽位；`physical_anchor` 是本次报告中的行/列/页/表格物理锚点。两者必须同时存在于表格 measurement 身份中：同一业务指标可出现在不同 physical anchor，同一行不同 logical slot 绝不能合并。

同比必须标记 `reported` 或 `derived`。程序只有在两个已批准、同口径、同单位、相邻期间 measurement 完整时才能计算 derived 同比。

### 12.2 第一版动作

动作字典初期只保留可明确判定的少量类型：

- `produces`：原文明确生产/制造某产品；
- `processes`：明确把输入加工/转化为输出；
- `sells`：明确销售产品或提供服务，不承载销售额/销量数字；
- `purchases`：明确采购某投入品；
- `provides_service`：明确提供某服务；
- `operates`：明确运营设施、平台或项目。

“拥有库存 100”不是 `stores` 活动的充分证据，而是 `inventory_volume` measurement。“销售量 100”不能仅因列名而生成 `sells` 活动；活动应来自业务叙述或表格对象的明确业务语义。

## 13. 主体口径决策树

主体范围仅允许：

- `consolidated_group`；
- `issuer`；
- `named_subsidiary`；
- `business_segment`；
- `unclear`。

判定顺序：

1. 读取报告封面、编制基础、表格标题、章节上下文和脚注；
2. 明确写“公司及子公司/本集团/合并口径”时选 `consolidated_group`；
3. 明确仅指上市公司母体时选 `issuer`；
4. 明确具名子公司时选 `named_subsidiary` 并保存名称；
5. 仅指业务板块且不能映射法律主体时选 `business_segment`；
6. 证据不足时选 `unclear`，禁止为了晋级强制二选一。

同一表格内共享且明确的主体口径可以由程序传播；跨章节、跨表格不得无证据传播。

## 14. 单位、比例和数值所有权

- LLM 和表格解析器只保存 `source_value`、`source_unit`、表头和脚注；
- 程序是唯一 canonical 换算 owner；
- 元、千元、万元、百万元、亿元必须按表头/脚注明示换算；
- 百分比与 fraction 必须由单位决定，不能按数值大小猜测；
- reported 与 derived 毛利率可以并存，但必须使用不同 provenance；只有 reported 时不得为了字段完整而编造 derived 记录；
- 披露精度参与 reconciliation 容差，但不能掩盖真实越界；
- 非标准单位、行业专用单位和复合单位由行业文档定义；未证明单位进入 `unclear` 或 `extraction_failed`。

## 15. 覆盖、页预算和失败诚实性

- required 章节和表格必须先进入覆盖计划；
- 显式页、标题锚点、表头锚点和跨页连续表优先于普通上下文；
- 超预算丢弃 required 页必须产生 `extraction_failed` 和 dropped-anchor 诊断；
- OCR 未完成、文本乱码或表格结构损坏不得标记 `not_disclosed`；
- 每个任务报告必须列出 requested、observed、not_disclosed、not_applicable、failed、unclear 数量；
- 一家公司某字段失败只能按明确策略影响该字段或该公司，不应让无关公司静默丢失。

## 16. 行业包体系

### 16.1 为什么需要行业包

通用骨架统一“对象、证据、时态、完备性和治理”，但不同行业对经营规模和核心驱动的表达不同。制造业关心产品收入和产销存，银行关心存贷款和资产质量，餐饮关心门店，平台公司关心用户与交易规模。用一个 prompt 和一个字段表覆盖全部行业，会迫使模型猜测不适用字段或遗漏真正重要字段。

### 16.2 初始行业族

| 行业族 | 共性关注点 | 说明 |
|---|---|---|
| 制造/材料 | 产品收入成本毛利、产量销量库存、披露产能、原料、加工链 | 第一优先研究 |
| 资源/矿业 | 资源量储量、品位、产量销量、开采/选矿/冶炼、矿权 | 独立文档后启用 |
| 能源/公用事业 | 装机/产能、发电/供给量、利用小时、用户和区域、燃料 | 独立文档后启用 |
| 消费/零售/餐饮 | 品类、渠道、门店、同店/客流（仅披露时）、区域 | 不假设必披露同店 |
| 一般服务 | 服务线、项目/合同、客户结构、人员或网点等规模 | 需再分子行业 |
| 金融 | 业务线、资产负债、资产质量、监管指标 | 与制造合同完全分离 |
| 医药 | 产品/管线、适应症、研发阶段、销售、集采 | 需明确事件与状态 |
| TMT/平台 | 产品服务、用户、交易/流量、变现模式、基础设施 | 指标披露差异大 |

商品价格、行情和外部宏观指标不属于公司披露 measurement；同店销售、监管指标等只有在行业文档定义且公司实际披露时才记录，不能列为所有公司的必填事实。

## 17. 按业务 regime 启用行业包

行业包不得按公司当前静态行业永久绑定。`IndustryPackageAssignment` 必须绑定 `instrument_id + report_period + business_regime_id`，并保存知识时点和证据。

### 17.1 启用依据

按以下证据综合确定：

1. 报告期有效的正式行业分类，作为候选而非唯一裁决；
2. 年报主要业务原文和主营构成；
3. 重大资产重组、借壳上市、资产注入/出售、控制权变化和主业变更公告；
4. 收入/资产/经营活动的实际主导结构；
5. 人工批准的 regime 事件。

开发者、LLM 或单一聚合源不得临时决定行业包。

### 17.2 主包与扩展包

- 每个 regime 有且仅有一个 `primary_package`；
- 可以启用少量 `extension_packages`，但每个扩展包必须有字段级触发证据；
- 通用基础包始终启用；
- 多包重名字段使用通用定义，不重复抽取；
- 行业特有字段由对应包拥有；
- 两包规则冲突时进入 `package_assignment_unclear`，不得选择更容易通过的一方。

### 17.3 转型、主业变更和借壳

出现以下情况必须评估新 regime：

- 原主业出售或大幅缩减；
- 重大资产注入、并购或借壳使收入和经营活动主导结构改变；
- 公司正式宣布主营业务变更；
- 报告期内存在新旧主业并行的过渡期；
- 行业分类变化且正式披露支持业务实质变化。

处理规则：

1. 关闭旧 regime 的业务有效期，但不改写历史报告；
2. 从有证据的生效日期开启新 regime；
3. 过渡报告可使用 `transition` regime，同时启用旧/新相关字段的最小组合；
4. measurement 继续绑定具体分部和主体，不能因包切换混合口径；
5. 无法确定生效时点或主包时，仅启用通用基础包并标记 `package_assignment_unclear`；
6. 新行业包未完成研究和批准时，不得用最相近旧包强行替代。

## 18. 行业研究方法和独立文档标准

### 18.1 研究原则

行业包必须从行业共性提炼，不从单个明星公司反推。每个行业先深读多份代表性年报，再确定结构、字段和 prompt。

代表性样本至少覆盖：

- 不同子行业和商业模式；
- 大中小市值或业务复杂度；
- 不同交易所和年报模板；
- 有/无标准经营数据表；
- 主业稳定、转型和重组公司；
- 正例、合法空披露、歧义和解析失败。

样本数不在总需求中机械规定；行业文档必须说明为何样本足以覆盖已知披露形态，并保留未覆盖边界。

### 18.2 每份行业文档必须包含

1. 行业边界、子行业和不适用范围；
2. 研究样本清单及选择理由；
3. 年报章节地图、标题别名和常见表格；
4. 研究员希望回答的问题；
5. 通用字段、行业特有字段和完备性级别；
6. 每个字段的数据结构、主体、期间、单位和证据要求；
7. 确定性解析规则和失败条件；
8. LLM extract/repair/verify prompt 合同；
9. 正例、反例、合法空值和冲突样例；
10. 多包组合和 regime 切换规则；
11. benchmark 金标准和验收指标；
12. 未解决问题与明确非目标。

### 18.3 行业文档登记表

阶段 2 的通用研究方法与模板已由 `define-company-profile-industry-research-method` 建立：

- 研究方法：`company_profile_industry_research_method.md`；
- 行业需求模板：`company_profile_industry_requirements_template.md`；
- 样本与 gold 标注模板：`company_profile_industry_sample_manifest.template.json`、`company_profile_industry_gold_annotation.template.json`；
- benchmark 验收模板：`company_profile_industry_benchmark_acceptance_template.md`。

方法和模板完成不等于任何具体行业已完成研究。登记状态统一使用 `requirements_baseline`、`not_researched`、`researching`、`in_review`、`approved` 或 `held`；阶段 2 结束时所有具体行业均为 `not_researched`，后续状态必须随独立行业研究和审核结果更新。

## 19. 多行业包组合

行业包组合由版本化 resolver 执行，但首个竖切在 resolver 自动化之前必须使用人工批准的 package manifest；resolver 只能实现行业文档明确的规则：

1. 加载通用基础包；
2. 根据报告期/regime 加载主包；
3. 根据明确业务分部证据加载扩展包；
4. 合并同名通用字段，保留包来源；
5. 对 extension-only required 字段，仅在触发条件成立后要求覆盖；
6. 对冲突定义 fail closed；
7. 将最终包集合、版本、启用证据和未决项写入运行 manifest。

首个试点的包集合、样本和报告期必须由人工批准 manifest 固定；在第二个行业包或第二个独立行业验收通过前，不得把人工 manifest 替换为全自动行业推断。任何阶段都禁止按公司名称、开发者配置便利或模型输出的单个行业标签随意叠加包。

## 20. 商品暴露与供应链边界

### 20.1 商品暴露

第一版只记录公司正式披露的产品、原材料、能源、产销存、套保标的等基础事实，并保留产品/商品映射接口。不承诺自动发布完整商品暴露，更不自动计算价格上涨对利润的方向和幅度。

商品行情来自独立行情数据域，不得混入公司年报事实。商品暴露发布必须以后续独立合同组合：批准事实、批准映射、明确角色、适用期和必要研究假设。

### 20.2 供应链地位

第一版允许保存：

- 年报明示的原材料和采购关系；
- 明示的客户、供应商和合同；
- 有完整输入/输出证据的加工转化；
- 由受控规则得到的有限角色候选。

第一版不要求回答“公司完整处于产业链哪一环”。`produces`、`processes`、`sells` 或某个产品事实不能自动推出全部上游和下游。终局研究视图可以组合已批准事实描述有限位置，但必须同时显示证据覆盖和未知部分。

## 21. DCF 与研究视图

### 21.1 DCF 边界

DCF 第一版只读已批准、时点有效的 reported measurement 和明确允许的 deterministic derivation。以下内容永远不能仅凭画像事实自动进入估值：

- 商品价格路径；
- 销量/价格预测；
- 毛利率预测；
- 传导率和 lag；
- 套保有效性；
- 完整产业链位置和竞争优势判断。

### 21.2 研究视图

v1 研究视图采用模板生成。若允许 LLM 润色，输入只能是已批准结构化记录和批准原文，输出不得新增数字、对象、角色、因果或未披露判断；新增任何事实即验证失败。

## 22. 跨期变化和事件

`BusinessEvent` 至少表达：事件类型、公告/报告证据、事件日期、生效日期、涉及主体/资产、旧 regime、新 regime、状态和不确定性。

跨期比较必须：

- 比较同 metric、同主体、同分部、同期间类型和可比单位；
- 区分公司披露同比与程序计算同比；
- 对重组导致的不可比明确标记；
- 不将一个报告期的叙述自动延长到未来；
- 不因当前主营改变而覆盖历史事实。

## 23. 市场范围

- 第一阶段覆盖 SSE、SZSE、BSE 的 A 股正式年度报告；
- BSE 使用同一通用合同，但行业文档必须研究其披露模板差异；
- 港股暂不启用，不能默认复用 A 股章节地图、公告体系和口径；
- 半年报、季度报告和专项公告仅在后续字段需求明确后按文档类型扩展。

## 24. 与现系统的关系

### 24.1 保留的底座

- 正式公告发现与 PDF 归档；
- 文档版本、更正关系和知识可得日；
- 页文本、表格、OCR 和 evidence；
- candidate/approved/rejected、review audit 和双时态；
- 队列、租约、checkpoint、运行身份和失败清理；
- 公共 LLM 网关。

### 24.2 替换的语义层

- 旧活动中混入 measurement 的模型；
- 缺少行业差异的统一大 schema；
- 旧 `llm_report.v2`、`atomic_extraction.v6` 及相应 prompt/selector 身份；
- 以空数组或 family complete 掩盖未覆盖字段的行为；
- 由活动直接拼接商品暴露和完整供应链地位的路径。

### 24.3 旧数据策略

新结构不以兼容旧测试语义数据为设计目标。新最小闭环验证通过后，单独制定 reset change：

1. 保留正式 PDF、公告元数据和可复用原始 evidence；
2. 导出旧语义数据删除清单；
3. 停止旧 writer 和 replay lookup；
4. 物理删除旧 activities、measurements、relationships、roles、exposures、runs、receipts、work、checkpoints 等新合同不可复用数据；
5. 从正式文档按新合同重建；
6. 不建立长期 legacy 兼容分支。

## 25. 当前七组冲突的解释与处置

`300750.SZ` 2025 年报现有七组 approved 冲突，本质是旧模型把同一表格行同时投影为 `issuer` 和 `consolidated_group` 活动，并把 measurement 压入 activity：

| 组 | 页 | 旧动作/对象 | 正确业务含义 |
|---:|---:|---|---|
| 1 | 25 | `sells / 动力电池系统` | 分产品营业收入行，含收入、成本、毛利率三个 measurements |
| 2 | 27 | `stores / 电池系统` | 电池系统库存统计 measurement |
| 3 | 26 | `sells / 电池系统` | 电池系统销量 measurement，不是销售额 |
| 4 | 25 | `sells / 储能电池系统` | 分产品营业收入行 |
| 5 | 26 | `produces / 电池系统` | 电池系统产量 measurement |
| 6 | 25 | `sells / 电池矿产资源` | 分产品营业收入行 |
| 7 | 25 | `sells / 电池材料及回收` | 分产品营业收入行 |

“电池矿产资源”在第一版仍是制造/材料包中的分产品收入标签，产品名称包含“矿产”不得自动触发尚未独立研究和验收的资源/矿业扩展包。

其中收入表原始字段为“项目、营业收入、营业成本、毛利率”，四个产品行均有独立业务含义。新合同实施前不在 issuer/consolidated_group 之间任选旧 canonical，也不继续为旧结构开发迁移兼容；这些记录随旧语义 reset 删除，并从原年报证据按 `Segment + Measurement + subject scope` 重建。

## 26. 分阶段实施

### 阶段 0：冻结旧链（本轮）

- 关闭旧 rollout、backfill 和 semantic production；
- 停止 10.3 与旧 schema 新写入；
- 保留原始文档、证据、审计和停止能力。

### 阶段 1：权威需求（本轮）

- 本总需求成为唯一权威；
- 建立 OpenSpec change；
- 标记旧 requirements/runbook 的历史状态；
- 明确行业文档模板、regime 包启用规则和实施顺序。

> 阶段 0/1 是 `define-company-profile-product-and-industry-contracts` 的唯一实施范围。以下阶段是长期路线图，每个阶段必须建立独立 OpenSpec change 并单独审核，不得作为本 change 的 `/opsx:apply` 待办继续展开。

### 阶段 2：行业研究方法与模板

- 创建行业文档模板和样本选择标准；
- 建立章节家族、字段字典、正反例和 benchmark 标注规范；
- 不开发抽取生产代码。

### 阶段 3：制造/材料行业共性研究

- 深读多份代表性年报；
- 形成制造/材料独立需求文档；
- 冻结第一版字段、章节和 prompt 合同。

### 阶段 4：通用模型和新 LLM 合同

- 实现 BusinessOverview、Activity、Measurement、Coverage、Regime、PackageAssignment 等最小模型；
- 实现 extract/repair/verify 严格合同；
- 使确定性表格优先和 LLM fallback 形成一条权威链。

### 阶段 5：制造/材料多样本竖切

- 新合同结果只写入隔离的新契约存储或明确命名空间，禁止混写旧 approved 表、旧 replay index 和旧发布路径；
- 用多家公司验证总体业务原文、产品收入成本毛利率、产销存和口径；
- 宁德时代只作为其中一个复杂样本；
- 研究员核验输出确实能回答第一版研究问题。

### 阶段 6：旧语义 reset

- 单独审核删除清单；
- 保留原始文档/证据，物理清理旧语义结果；
- 按新合同重建样本。

### 阶段 7：逐行业扩展

- 每个行业独立研究、独立文档、独立 OpenSpec、独立验收；
- 不因通用框架存在就批量开启未研究行业。

### 阶段 8：恢复批量生产

- 只有新合同、行业包、benchmark、失败清理和 reset 均通过，才重新打开 backfill；
- 先小样本、单行业，再扩大范围。

## 27. 业务验收标准

### 27.1 阶段 0

- 旧 backfill 命令不能启动新的语义生产；
- 旧 semantic production 不写新事实；
- 原始文档获取、本地审计和停止能力仍可用；
- 没有删除生产数据。

### 27.2 阶段 1

- 本文件进入 `docs/README.md` 唯一 current/requirements 索引；
- 旧文档清楚标记为历史，不再与本文件竞争权威；
- OpenSpec proposal/design/spec/tasks 对齐本文件；
- 第一版范围、非目标、对象、完备性、来源、章节、LLM、行业包、regime、商品/供应链、DCF 和旧数据策略均有明确要求；
- 后续每项任务可以映射到需求条款和业务验收，不能靠开发者自行补定义。

## 28. 文档一致性矩阵

后续每次 OpenSpec 或行业文档审核必须核对：

| 主题 | 总需求 | 行业文档 | OpenSpec spec | tasks | prompt/schema | 测试 |
|---|---|---|---|---|---|---|
| 产品问题与范围 | 必须 | 细化 | MUST | 映射 | 不扩面 | 验收问题 |
| 字段定义与完备性 | 通用 | 行业级 | MUST | 实现 | 同名同义 | 正/空/失败 |
| 章节和来源 | 原则 | 具体地图 | MUST | selector | 输入一致 | 多模板 |
| 主体、期间、单位 | 通用 | 行业例外 | MUST | validator | 必填 | 边界 |
| 行业包/regime | 通用规则 | 启用细节 | MUST | resolver | manifest | 转型/借壳 |
| LLM 分工 | 三类请求 | 主题 prompt | MUST NOT | adapter | 严格 schema | 幻觉/遗漏 |
| 旧链退场 | 冻结/reset | 不适用 | MUST | migration | 禁写旧版 | 无旧写入 |

若同一概念在两层出现不同枚举、范围或成功标准，change 不得进入实现。审核目标不是文档篇幅，而是确保每个业务问题、字段和失败状态在各层含义一致。
