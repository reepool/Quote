# A/B 角色开发与审核流程

> 类型：current；版本：1；制定日期：2026-10-14。
> 适用：Quote 中采用 A 角审核、B 角开发的任务；业务目标和数值门槛由当前 OpenSpec / 任务卡确定。
> 生效：A 下次收到开发交付并完成审核推进时，一并告知开发者，并在后续任务卡中引用本流程。该次已完成或在途交付继续按原合同审核，不追溯改变首次成绩、授权或审批点。

本流程用于减少范围内修复的等待、重复机械核验和交接成本，同时保留独立业务审核。它不改变业务 owner、生产权限、样本范围或验收阈值，不要求新建审核平台、调度器或通用测试框架。

用户的明确指令及当前任务的显式限制优先；只读审核、仅观察 / 登记失败的任务不因引用本流程而获得实现授权。

## 1. 职责与唯一交接点

| 角色 | 负责内容 | 交付 / 停止位置 |
| --- | --- | --- |
| A：审核与推进 | 明确业务验收、任务边界及 B 的自主范围；独立检查原文语义、真实输出和直接回归；裁决合同冲突；给出通过结论和下一张卡 | 发现阻塞时给出可定位的证据及修复条件；通过后明确允许的收口和后续工作 |
| B：开发与自检 | 沿唯一业务 owner 实现、局部闭环、范围内修复、相关回归、代码冻结、正式复验和材料交接 | 在卡内连续推进到达标提交，或确实需要新裁决 / 授权时报告阻塞；达标后等待 A 的有限验收 |

A 的审核不能用 B 的 `accurate=true`、测试全绿或相同匹配函数复算代替独立原文判断。B 的开发自检与 A 的业务验收分开；A 的非阻塞建议不自动变成 B 的任务。

沟通通过现有任务卡和审核回复完成，不增加外部通知或新的逐步审批。默认 A 只审核和规划；若需 A 实现修复，应有明确任务授权。

## 2. 任务卡先明确自主范围

A 发卡时使用以下简短结构，已有 OpenSpec 内容可直接链接，不另写重复规格：

```text
目标与验收：<可观察业务结果、冻结来源 / 范围、通过条件>
入口与边界：<唯一 owner、输入输出、兼容 / 生产不变量、非目标>
自主推进：实现 → 局部闭环 → 卡内 P0/P1 修复 → 直接回归 → 正式复验 → 达标提交。
运行约束：<目录 / 版本、每轮及整卡适用的时间和 token 预算、授权的正式尝试范围 / 数量>
需裁决：合同与原文冲突；需改变范围、验收口径、权限；预算不足；既有改动无法隔离。
交接：一个提交入口，链接首次结果、差异、核验回执和来源证据。
完成：A 有限通过后的规格同步 / 归档及下一步，以本卡明确授权为准。
流程：docs/development/ab_role_development_workflow.md（v1）。
```

采用本流程的新卡，默认允许 B 连续完成本卡业务闭环及其中的 P0/P1 修复，不因可在卡内解决的首次失败再次等待 A 同意。任务中的 P2/P3 依赖和验证工作也在已声明范围内。预算和尝试次数沿用任务合同，不因“自主推进”变成无限授权；若合同只有单轮预算，不得自行宣称获得无限多次正式运行授权。

若现行 OpenSpec / 卡仍要求失败后仅登记或待 A 核定，A 发后续卡时须同步明确其流程授权，消除与自主推进的冲突；B 不得自行把原暂停条款解释为已取消。

原合同与原文冲突时，保留原合同和原分数，另列证据及建议口径，先请求 A 裁决。B 可继续不依赖该裁决的工作，不得改分母、别名或预期来消除失败。

## 3. B 的连续开发闭环

1. 记录 Git 基线，核当前目标、业务入口、直接调用链和必要来源；保护既有改动。
2. 对未见样本，先独立阅读来源并冻结合同，再按既有程序执行首次观察；不能先用该样本调试业务代码或预演输出，再称其为未见首次成绩。
3. 首次观察失败时，立即保护原结果，按真实错误类型定位 P0/P1；在新卡授权范围内直接进入同源局部修复。暂停的是后续样本 / 扩批，卡内修复及后继复验可继续。
4. 用当前完整业务输入打通局部接受、查询和导出；补上实际触发的边界。将“某页出错”解释为可检验的规则，如交易对手续行、收入空位借列、章节适用状态或主体期间误升格。
5. 运行直接受影响的旧样本正反例。已有真实跨公司同类样本可用于证明适用性；没有时据实说明，不为凑数量另建框架或扩大抓取。
6. 正式复验前，完成局部逐对象自检、实质正文核查及必要代码 Review，再冻结来源、代码和执行身份。后继正式轮使用新目录 / 身份，不覆盖首次结果。
7. 正式复验达标后提交 A；失败则保留该轮结果，继续在卡内定位。发现正式轮后的局部补正不能改写该轮成绩，须经后继正式轮证明，除非原验收合同明确采用其他验证方式。

同一根因再次导致正式失败时，先返回局部闭环找出未验证的路径，不以连续新增版本或盲目重跑代替定位。非阻塞架构、性能、风格和无关旧问题后置。

## 4. 继续与暂停的边界

| 情况 | B 的下一步 |
| --- | --- |
| 冻结范围内漏项、错误事实、直接回归，可在既有 owner 内修复 | 连续修复、定向验证及卡内后继复验，不新增审批点 |
| 原文 / 合同冲突，或须改变分母、验收口径、样本 / 权限范围 | 保存证据和原成绩，请求 A 裁决；只继续独立工作 |
| 达到预算 / 尝试限制，或无法安全隔离既有改动 | 报告具体阻塞及已完成内容，不越限或覆盖他人改动 |
| 达到卡内正式门槛，等待有限验收 | 提交 A；不自行归档、扩批、启用生产或扩大质量声明 |
| A 发现范围内阻塞 | 修复该阻塞和直接回归，按原合同复验；不把非阻塞建议加入范围 |

A 通过后，B 可执行审核回复 / 任务卡明确授权的规格同步与归档，无需对已授权步骤重复询问。下一对样本仍须有明确后续任务卡，有限通过不自动授权更大批量或生产。

## 5. A 的独立审核

审核按结果错误风险排序：先核业务是否真实交付和正文是否实质完整，再核收入、动作、主体、期间、栏目、空位、单位、合同外输出及直接回归。不能以大量收入记录替代主营业务完整性。

- 对首次观察，保留真实漏项和错误；确认合同独立于输出，未发布 / 未检查不能算负例通过。
- 对修复交付，重点挑战新规则、曾出错的边界和受影响旧正反例，检查是否存在未经原文支持的公司特例。
- 所有实际输出仍按当前合同纳入准确率；要求逐对象复核的任务继续逐对象核查。风险抽查用于选择独立挑战点，不能替代全量计分或将抽查通过表述为全量100%。
- 共享程序可计算计数、哈希和一致性，语义判定仍须有原文依据。合同外事实和正文必须有实际来源支持。
- 发现阻塞时说明具体输入 / 原页、错误对象、错误行为及验收条件；修复后只审核相关变化和必要回归。无已知阻塞且证据满足合同即结束，不追求零建议。

审核结论分为有限通过、范围内阻塞、需合同 / 授权裁决，明确事实覆盖范围、实测限制和下一步。合同有冲突时，A 能在现有需求和权限内依据原文解决的，直接裁决并记录；需要用户选择或新权限的，才向用户提问。

## 6. 机械核验复用与安全

同一代码、合同和制品快照使用一份现有核验入口及结果；A 检查命令、实现、输入版本、实际输出和回执，不默认再完整跑一遍相同机械检查。

只有输入 / 代码改变、回执缺失、结果不一致、实现存在疑点或必要独立复验时才重跑相关部分。复用不能把上一版结果套到新代码，也不能仅依赖提交说明中的通过声明。

审核用核验须只读历史结果、来源及业务数据库。需要临时输出的测试使用隔离目录 / 数据库，不覆盖提交者的诊断、首次制品或审核证据；带写入副作用的评分脚本不能直接当只读审核工具执行。

优先复用已有脚本并明确其副作用；确有重复操作需要收口时，仅做当前调用所需的最小修改，不以本流程新增审计平台。历史原件继续保护，材料减少针对重复说明，不删除尚需保留的证据。

## 7. 一个固定交接入口

B 在现有 `review-submission.md` 或本轮同用途文件集中提交下列信息，详细证据直接链接，不另建平行状态文档：

```text
结果：首次 / 后继正式轮；冻结合同、实测分数及覆盖限制；待 A 判断什么。
差异：基线与提交 / 执行代码身份；业务规则变化；修复的阻塞及原行为保留情况。
验证：实际运行的局部 / 回归 / 静态检查、失败或后置项；正式轮资源及状态。
证据：原来源、首次结果、后继正式结果、逐对象 / 正文判定、只读核验及保护回执。
闭环：Git 提交与推送、既有改动保护、剩余阻塞、下一步请求。
效率：B 活跃开发时间、交接等待时间、正式复验次数及重复根因；无法准确统计时标明未知 / 估算。
```

A 的回复给出结论、关键依据、剩余阻塞和后续任务卡，并补记 A 活跃审核时间及新发现的阻塞数。不要求新计时系统；等待和运行时间不能混称开发时间，业务运行的 token 不能代表 A/B 开发及审核消耗。

## 8. 两轮试行与流程复核

新流程试行两轮后，利用现有交接记录比较首次业务表现、同类缺陷复发、正式复验次数、A 新发现阻塞、活跃开发 / 审核及交接等待时间。不同样本分母和披露难度须分列，不能仅凭两个不同样本的召回百分比宣称优化有效。

这些记录用于选择下一项流程改善，不增加业务通过门槛；缺少时间记录不阻塞业务验收。不得为改善指标降低验收要求、减少重要披露条件或扩大生产权限。已修样本100%与未见样本首次表现分别报告。

公司画像后续执行卡同时引用`company_profile_acceptance_program.md`（v1），按其12/20/100固定数量、首发/补救双列、分级交付及停止规则推进；唯一进度表位于该计划，不在本流程另建状态副本。该计划明确要求的补救成本应记录，无法评估不能宣称该项通过；本节一般效率记录仍不单独增加门槛。在途冻结合同继续按原门槛审核，切换须由A在新执行卡明确接续，不用新容错标准追溯改写历史结果。

## 9. 下次审核推进时的开发者告知

A 下次收到开发完成的提交时，先按该次原任务合同审核；在同一审核推进回复中附以下告知，并将 v1 引用及自主范围写入后续卡：

> 后续任务采用 `docs/development/ab_role_development_workflow.md`（v1）。B 在任务卡范围内连续完成实现、局部闭环、P0/P1 修复、直接回归及正式复验；首次失败保留，暂停扩批但不暂停已授权的同源修复。达标提交 A 有限审核。合同冲突、范围 / 权限变化、预算不足或既有改动无法隔离时请求裁决。提交使用一个证据入口；机械核验复用当前快照的只读回执，A 独立审核业务语义。原验收阈值及生产 / 规模边界不变。

如当次存在阻塞，告知适用于后续修复卡，不表示该次已通过。不得只贴链接而遗漏任务卡的执行范围、运行约束和停止条件。已冻结的在途卡若要切换流程，须由 A 在该次推进回复中显式更新其流程授权，原合同、来源、首次结果和分数保持不变。

首次告知后，在启用流程的现有任务卡 / 提交入口记录流程版本和 A 的审核推进回复位置。后续已有该记录时引用流程即可，无需每轮重复完整告知；不为此新增平行状态文档或修改冻结原件。
