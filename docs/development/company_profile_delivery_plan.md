# 公司画像交付路径与开发任务卡

> 类型：requirements / execution plan；版本：2；2026-10-16。
> 业务定义见[产品总需求](company_profile_product_and_industry_semantic_requirements.md)，全部数值门槛/预算/进度只以[验收计划v2](company_profile_acceptance_program.md)为准；本文件不复制成绩台账。
> 唯一实施change：[restore-company-profile-llm-led-generalization](../../openspec/changes/restore-company-profile-llm-led-generalization/proposal.md)。本次批准规划与任务顺序，不运行付费调用、盲测或生产。B可开始卡1实现及离线验证；真实运行须具备该卡的模型/价格/预算绑定和A执行授权，不能用旧双公司余量。

## 1. 开发者必须先理解的纠偏

交付是“读懂年报后给研究者公司画像、产品暴露、供应链定位”，不是“恢复尽可能多附注行”。程序整理PDF和有把握的结构化数值、约束身份/单位/证据和写入；LLM负责开放语言理解、主次判断、语义覆盖和证据内摘要。原始事实与摘要分开，推断与披露分开。

现有公告、PDF/布局缓存、Evidence、事实模型、队列、公共LLM网关和查询/导出继续使用。修正`provider=None`可成功冒充语义完成、同field短路、正则决定全文可见性/正文完整性的路径。不要新建agent平台、网关、审计系统或并行writer。

业务链：正式年报 → 全页结构/有界语义发现 → 核心上下文阅读及可靠数值 → 源先行漏项对照/证据核验 → 三视图与不确定项 → 既有owner保存/查询/导出。

## 2. 管理方法与审核顺序

每次开发/审核必须按此顺序，不得直接从上轮修复卡继续扩大：

1. 读取产品总需求、验收计划唯一进度表、本文件当前卡、A/B流程v2，再看change及本次证据。
2. 明确当前阶段、三类产品还缺什么、真实路径是LLM/解析/语义缓存哪一种，剩余公司数/预算/重试数。
3. B在同一owner内连续完成实现、直接回归、限额内P0/P1修复；来源合同变更单独裁决并保存原分母/分数。纯风格和无关旧失败后置。
4. A先核真实调用和源覆盖，再独立核三视图及高风险事实，最后看统计/运行/工程检查。不能用同一个匹配器、字段存在或`accurate=true`代替语义审查。
5. 分别给出首次/补救、自动/人工、样本实测/全市场估计、通过/限用/失败；同步唯一进度表。只推进到下一张有依赖和预算的卡。

工作在途上限：一张核心实现卡；源材料可并行准备，未见样本不得预演调参。每张卡最多两个共性修复迭代，若仍不满足目标就提交原因与取舍，不自动生第三轮。L0/L1每个工作日结束记录“已完成业务、阻塞、下一步”；连续两个工作日没有新业务可用证据时A重新审查路径，不派生平台建设。S2每5家、S3每20家、S4每波出检查点；无需逐家公司等待批准。

只用现有`review-submission.md`交接：输入/版本、三视图样例及证据、模型调用/usage、首次与补救统计、分级与限制、测试、预算、下一步。常规审核成本、人工补救成本、机器运行成本分列。A必须说明当前离终点还差哪个门槛，不能仅回复“有限通过，再换两家”。

## 3. 顺序开发任务卡

### 卡1 / L0：一家公司真实解读闭环（当前首要任务）

- 目标：从已有历史报告选1家同时含主营描述、收入表及投入/角色的公司，真实LLM生成三视图，并从query/export读回；选择不得触碰S2留出20家。
- 入口/owner：`company_profile_common_core` → `research/company_profile/operations.py` → runtime/workflow及`CommonGatewaySemanticProvider` → 原repository/read service；统一走`utils/llm`公共网关。
- 实现：先绑定provider与可核日志，再接全文发现、源先行核心清单、证据摘要；将同field短路限定为可靠结构化事实复用；拆开硬校验与语义判断，正则只作定位提示/风险提示。必要请求/读取元数据版本化，不向旧schema偷偷塞字段。
- 输出：三视图、原文引用、缺项/冲突说明、真实模型/请求/usage、页覆盖、query/export一致；provider未配置或不可用明确失败/限用。
- 验证：同一报告完整端到端；增加缺provider、已存在overview仍需语义阅读、否定/计划/第三方及真实冲突的直接测试；源先行检查要能找出故意移除的主要板块。模型调用量不作为质量替代。
- 自主范围：上述调用链的最小充分修改、直接旧回归、一次局部修复；运行按验收§7的L0/L1累计上限，冻结模型配置和费用后执行，不接下一对规则轮次。
- 停止：无真实调用、核心语义被规则误判、底线错误无法隔离、预算耗尽或既有改动不可安全隔离时提交阻塞。通过后进入卡2，不直接跑S2。

### 卡2 / L1＋S1：四类通用性与已知回归

- 输入：历史公司中制造、非金融服务、金融、综合各1家，共4家，包含L0那1家；沿同一实现，不加公司/代码/页码生产分支。
- 交付：4家三视图及源审查；新句式/续页/未披露/冲突均可表达；有歧义的可正确限用，但不能把主营缺失包装为通过。4家最终均达到公司可用标准才进入S1。
- S1：原12家公司在最终同一版本回归，覆盖六类已知风险；各自至少一次真实语义结果与源核验，固定结构化回归仍运行。正文按原文支持的业务含义验收，不要求逐字模板一致；旧Gold与原文冲突单列裁决，不为过测试改正确含义。旧规则12/12不能顶替新链验收。
- 验证：保留首发失败，12家核心正反例全过，不要求全部附注明细恢复；报告冷/热解析、请求/token/费用、总时长。用4家和12家实测决定是否能在既定成本内进入S2，超预算先裁决，不偷偷改阈值。
- 清理：按§4退役已被替代的语义规则和旧默认绕行，移除失效临时执行脚本；保留有依据的表格解析及测试材料。S1真实调用和离线回归分列。
- 停止：达到修复/预算上限仍不具备通用性，则回到方案裁决，不新增第5家调参以稀释失败。

### 卡3 / S2：20家公司未见首发验证

- 前置：卡2通过；复核原20家仅来源准备、未业务预演。保留旧221正向/45负例合同，新增三视图条件采用新版本；若证实有污染，按预冻候补换入并报告原因，不称污染样本未见。
- 冻结：名单/分层/官方源/时间、独立核心条件及抽样种子、代码/模型/提示词/预处理、预算/权限；不沿用v61执行身份及300秒双公司授权。
- 执行：20家公司同版首发全部留存，中途不能看输出调参；每5家进度检查；失败后按验收§6有界补救并同版整组核验。
- 验收：严格引用验收§4–7的三视图、公司可用率、宏召回、已审准确率、底线和补救成本；未达首发指标不能用修复后成绩改判。
- 停止/下一步：首次20失败最多修三类主要根因，回归后仅一次新20确认；第二组失败结束本方案，不追加第41家。达标后只推进卡4准备。

### 卡4 / S3：100家公司受控研究试运行

- 输入：另100家未见报告，按验收计划分层；同版首次，禁止挑样/混版最好成绩。
- 交付：三视图、失败可查、单公司失败不中断他人、停止/恢复/幂等、更新时只处理变化报告、审计与补救成本。每20家检查点。
- 验收：首发≥90家可用、补救后≥95家，其他门槛仍按验收计划；到100家即结论，失败不加第101家。
- 通过后：A给出有限研究适用范围与S4具体上线/资源方案；不自动开启生产、DCF、交易或宣称全市场99%。

### 卡5 / S4：数千家公司自动覆盖与持续更新

- 输入：冻结时点全部SSE/SZSE/BSE A股名单N，缺年报也留分母；S3同报告同语义版本的合格成果可复用并标明。
- 交付：按验收§9的100→500→其余每波≤500处理；现有队列限并发/续跑，每家公司有三视图或具体缺失状态；聚类追查同类错误，不逐公司写规则。
- 验收：全名单状态覆盖100%、可读资产技术交付≥98%、抽审质量/可用率符合验收§9，保留未披露与未处理区别；14天完成目标以实测吞吐与获批预算为前提，成本/延迟超限明确未过。
- 权限：必须单独冻结N、并发、费用总额、时间、发布消费者及停止条件并获授权；按波推进，可研究发布，不自动授权投资决策。

### 卡6 / 行业增强：通用链稳定后才开展

- 从S3/S4反复出现且影响研究的问题中选择一个行业家族、最多3个关键指标（如银行息差/资产质量、制造产能/产销、资源储量/产量）。
- 每包4家开发＋另6家未见验证；增量字段已审准确率≥98%、核心增量召回宏平均≥90%、6家中≥5家可用且无未隔离底线错误；最多两次修复仍失败则停用该增强，通用画像继续。
- 指标、单位、报告期、适用范围和未披露状态明确。行业规则是解释框架和字段语义，不是逐公司枚举；不预建全行业包。
