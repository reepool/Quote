# A 股公司业务画像与商品暴露数据治理需求说明书

> 状态：需求与可行性评估基线
> 日期：2026-07-16
> 适用范围：A 股上市公司，第一阶段服务专业 DCF 的行业模型选择、周期归一化与商品驱动
> 关联文档：`professional_dcf_requirements.md`、`commodity_futures_market_data_requirements.md`
> 采集实施方案：`company_business_profile_data_acquisition_execution.md`

---

## 1. 结论

该能力可行，但不应被定义为“一次性解析全部年报并自动判断公司商品敏感性”。合理方案是建设一个以官方披露证据为基础、按行业逐步上线、允许人工复核的业务事实与暴露治理层。

免费公开信息能够覆盖大部分核心事实：主营产品、业务分部、收入构成、产销量、产能、储量、主要原料、部分单位成本、采购销售合同和套期保值。主要困难不是信息完全不存在，而是披露位置、名称、单位、合并口径和年度间格式不统一。

本地现有 `company_profiles` 表为 0 行，且其结构主要面向公司名称、上市日期、原始行业等基础资料快照。它可作为公司基础档案入口，但不足以承载多期、多分部、多产品、多证据的业务事实。应新增规范化事实表和映射表，不应将复杂结构继续塞入单行 `profile_json`。

建议首期只覆盖煤炭、有色金属、钢铁、石油石化、基础化工及部分建筑材料公司。先做到“能解释公司生产什么、处于哪一环、哪些商品是收入或成本驱动”，再扩展精确弹性、单位成本曲线和储量估值。

## 2. 目标与非目标

### 2.1 目标

1. 建立公司、业务分部、产品、价值链角色和商品之间的可审计关系。
2. 为 DCF 同时提供“申万行业默认”和“公司披露证据”两套画像。
3. 自动识别资源生产商、加工商、贸易商、下游制造商和综合企业。
4. 以估值日为截止日期读取当时已公开的事实，避免未来信息泄漏。
5. 支持商品价格、价差、产量、单位成本、产能和储量进入周期 DCF。
6. 对低置信度、口径冲突和多业务抵消情况生成复核任务，而不是强行给出结论。
7. 将证券法律身份与经营业务画像分离，长期保留借壳、重大重组、业务出售和新增主业前后的画像版本。

### 2.2 非目标

1. 首期不承诺覆盖全部 A 股公司的全部业务事实。
2. 不从公司名称或申万行业直接推断精确收入弹性。
3. 不使用无法定位原始证据的聚合网站标签作为生产事实。
4. 不把大语言模型输出直接写成已审核事实。
5. 不在 DCF 运行时临时联网解析 PDF。
6. 不首期建设港股披露适配；港股单独立项。

## 3. 使用场景

### 3.1 模型选择

- 申万三级行业负责给出稳定、权威的行业身份。
- 公司业务画像负责识别实际业务结构和公司特性。
- 行业模型与公司特性模型分别评分；两者接近或冲突时返回双模型结果。
- 银行、保险、证券等监管属性继续作为硬约束，不被商品画像覆盖。

### 3.2 商品周期归一化

资源生产商使用商品售价、产量、现金成本和资本开支；加工企业优先使用产品与原料价差；下游制造商使用原料成本暴露并结合转嫁能力。综合企业按分部拆分后再汇总。

### 3.3 DCF 审计与底稿

API 和 xlsx 底稿应展示：

- 行业默认画像；
- 公司特定画像；
- 商品或价差映射；
- 证据来源及报告期；
- 置信度、复核状态和生效日期；
- 哪些驱动已进入估值，哪些仅作为诊断；
- 行业模型与公司模型的估值差异。

## 4. 数据对象与必需字段

### 4.1 公司基础档案 `company_profile_snapshots`

现有 `company_profiles` 可继续承担这一职责。

| 字段 | 含义 | 必需性 |
|---|---|---|
| `instrument_id` | 统一证券标识 | 必须 |
| `company_name` / `short_name` | 公司名称 | 必须 |
| `exchange` / `listed_date` | 市场和上市日期 | 必须 |
| `registered_name` | 法定公司名称 | 建议 |
| `business_scope_raw` | 工商或披露原文经营范围 | 建议 |
| `company_intro_raw` | 公司简介原文 | 建议 |
| `source_document_id` | 来源文档 | 必须 |
| `report_period` | 适用报告期 | 必须 |
| `data_available_date` | 实际或估算可得日 | 必须 |
| `evidence_tier` | 官方、公司、辅助来源 | 必须 |

### 4.2 业务分部事实 `company_business_segments`

每行表示公司在某报告期的一个披露分部。

必需字段：

- `instrument_id`、`report_period`、`segment_id`、`segment_name_raw`；
- `segment_name_normalized`、`segment_type`；
- `revenue`、`revenue_share`、`segment_profit`、`segment_assets` 中可得项；
- `currency`、`consolidation_scope`、`geography`；
- `source_document_id`、`page_number`、`section_path`、`evidence_text_hash`；
- `data_available_date`、`extraction_method`、`confidence`、`review_status`；
- `valid_from`、`valid_to`、`version`、`lineage_hash`。

`segment_type` 建议枚举：`product`、`service`、`geography`、`customer`、`other`。不能把地区分部与产品分部相加。

### 4.3 产品与经营量事实 `company_operating_facts`

| 事实类型 | 示例 | DCF 用途 |
|---|---|---|
| `production_volume` | 原煤产量、铜精矿产量 | 收入驱动 |
| `sales_volume` | 商品煤销量、钢材销量 | 收入驱动 |
| `average_selling_price` | 吨煤售价、吨产品售价 | 价格驱动 |
| `unit_cost` | 吨煤成本、现金成本 | 利润率归一化 |
| `capacity` | 年产能、设计产能 | 中期上限 |
| `capacity_utilization` | 产能利用率 | 周期与爬坡判断 |
| `reserve_or_resource` | 可采储量、权益资源量 | 矿业寿命及 NAV 辅助 |
| `recovery_rate` | 选矿回收率 | 产量转换 |
| `yield_rate` | 加工成材率 | 加工模型 |
| `inventory_volume` | 商品或原料库存量 | 周期及营运资本 |

每条事实必须包含数值、单位、口径、分部或项目范围、报告期、可得日和证据定位。单位换算值与原始披露值必须同时保留。

### 4.4 价值链角色 `company_value_chain_roles`

建议枚举：

- `resource_owner`：拥有矿权、油气田或资源权益；
- `upstream_producer`：采掘或初级生产；
- `processor`：冶炼、精炼、裂解、化工转化；
- `integrated_producer`：上下游一体化；
- `trader_or_distributor`：贸易与分销；
- `downstream_manufacturer`：以商品为主要投入的制造企业；
- `utility_or_consumer`：能源或原料消费方；
- `service_provider`：油服、矿服、物流等间接暴露。

角色应按分部记录，并包含收入占比或重要性等级。公司级角色是分部结果的汇总，不是单标签覆盖。

### 4.5 商品暴露映射 `company_commodity_exposures`

| 字段 | 说明 |
|---|---|
| `scope_type` / `scope_id` | company 或 segment 及其标识 |
| `commodity_id` | 规范商品主数据标识 |
| `exposure_role` | revenue、feedstock_cost、energy_cost、inventory、hedge、spread_leg |
| `direction` | positive、negative、mixed |
| `materiality` | 收入占比、成本占比或 high/medium/low |
| `mapping_basis` | industry_default、company_disclosure、manual_review |
| `price_series_id` | 对应期货、现货或指数序列 |
| `spread_definition_id` | 加工价差定义，可空 |
| `lag_days` | 价格传导滞后 |
| `pass_through_score` | 成本转嫁能力 0-1 |
| `hedge_adjustment` | 套保对短期暴露的调整 |
| `confidence` | 映射置信度 0-1 |
| `effective_from/to` | 有效期 |
| `evidence_id` | 证据引用 |
| `review_status` | candidate、approved、rejected、superseded |

### 4.6 合同与套期保值事实

至少支持：长协销量占比、定价公式、基准价格、价格调整频率、take-or-pay、采购锁价、期货套保品种、名义数量、套保期限和会计套保标识。

仅披露“开展套期保值业务”不能直接推导套保比例；无数量和期间时只形成定性事实。

### 4.7 证据对象 `business_profile_evidence`

每个生产事实都必须指向证据对象：

- 来源机构、URL 或公告标识、文档哈希；
- 文档类型、标题、报告期、发布日期；
- 页码、表名、章节路径、原文片段哈希；
- 下载时间、解析器版本、OCR 状态；
- 实际或估算可得日及质量标识；
- 自动抽取置信度、审核人和审核时间。

## 5. 免费公开数据源评估

### 5.1 第一层：官方披露，生产主源

| 来源 | 可获得信息 | 稳定性 | 主要限制 |
|---|---|---|---|
| 巨潮资讯 CNInfo | 年报、半年报、问询回复、临时公告、附件 | 高 | PDF/HTML 格式差异大，需公告索引与附件治理 |
| 上交所 | 沪市公告、互动问答、监管文件 | 高 | 反爬和页面接口可能调整 |
| 深交所 | 深市公告、互动易 | 高 | 结构化经营数据有限 |
| 北交所 | 北交所公告及问询回复 | 高 | 样本较少，格式仍需适配 |
| 交易所/行业主管部门 | 产量、库存、行业统计 | 中高 | 多为行业层，不能直接代表公司 |

可行性判断：官方定期报告足以建立绝大多数公司的主营、分部和基础商品关系，是首期可依赖的免费来源。产销量、单位成本和储量的覆盖率会因行业和公司而明显不同。

### 5.2 第二层：发行人公开材料，补充源

- 公司官网投资者关系栏目；
- 年度业绩说明会材料和演示文稿；
- 公司可持续发展报告、矿产资源或产能公告；
- 交易所互动平台中经公司确认的答复。

这些来源可补充经营口径，但可能选择性披露、链接失效或缺少统一文档编号。必须保留下载副本哈希和可得日，证据等级低于法定定期报告。

### 5.3 第三层：免费聚合接口，候选发现源

AkShare、BaoStock、东方财富、同花顺公开页面可帮助获得公司简介、主营构成标签或快速定位文档，但接口和字段稳定性不足，且部分数据缺少可追溯的原始披露。生产规则为：

1. 可用于生成候选公司、关键词和文档定位任务；
2. 不得单独把精确商品暴露或数值事实提升为 `approved`；
3. 与官方披露冲突时以官方披露为准；
4. 页面接口变化不得阻断已有事实读取和 DCF 运行。

### 5.4 暂不依赖的数据源

Wind、Choice、同花顺 iFinD、彭博、Refinitiv 等付费终端可能显著降低人工整理成本，但不是本项目免费数据基线。后续可作为 provider 插件接入，不能成为首期生产必需依赖。

## 6. 自动治理算法

### 6.1 行业默认候选

以估值日有效的申万三级行业为入口，加载行业模板：候选价值链角色、典型产品、原料、相关商品、常用价差和默认方向。行业模板只提供候选，不直接成为高置信度公司结论。

### 6.2 公司证据抽取

处理顺序：公告目录筛选、PDF 原生文本提取、表格提取、必要时 OCR、章节定位、字段抽取、单位归一化、实体消歧、证据回链。优先规则和字典，语言模型只用于候选抽取和归一化建议。

重点章节：主营业务分析、分行业/分产品收入成本、产销量、重大在建工程、矿产资源与储量、采购销售模式、套期保值、风险因素和管理层讨论。

### 6.3 置信度评分

建议字段级评分，不设一个笼统的公司总分：

`confidence = source * evidence * entity * unit * consistency * recency`

各因子取 0-1：

- `source`：法定报告 1.00，公司演示 0.85，互动问答 0.75，聚合候选不高于 0.50；
- `evidence`：结构化表格高于叙述文本，能定位页码和表头高于仅关键词命中；
- `entity`：明确属于上市公司合并口径或指定分部为高；
- `unit`：原单位、换算和期间口径明确为高；
- `consistency`：跨表、跨期和财务合计可勾稽为高；
- `recency`：当前有效事实高于多年以前且未确认持续有效的事实。

生产建议阈值：

- `>= 0.85` 且通过规则校验：可自动批准低风险分类事实；
- `0.65-0.85`：进入人工复核；
- `< 0.65`：仅保留候选，不进入 DCF；
- 精确弹性、单位成本、储量和合同定价无论分数多高，首期均需抽样或人工审批。

### 6.4 行业模型与公司模型的决策

分别计算：

- `industry_model_score`：行业身份权威性、行业模板成熟度、财务行为匹配度；
- `company_model_score`：公司证据覆盖率、材料性、时效性、分部集中度、经营量可得性；
- `conflict_score`：行业模板与公司证据方向、角色和分部权重的冲突程度。

规则：

1. 公司证据充分且集中时推荐公司特性模型；
2. 公司证据不足时推荐行业模型，但标识为默认画像；
3. 分数接近或冲突较高时返回两套估值；
4. 多元化企业按分部模型或 SOTP，不强行选一个商品；
5. 所有评分项和阈值进入 API 与底稿。

### 6.5 自动复核规则

以下情况必须进入人工复核：

- 产品名称无法映射唯一商品；
- 同一商品同时是主要产品和主要原料；
- 分部收入合计与财务收入差异超阈值；
- 数量与金额隐含单价偏离市场合理区间；
- 单位、币种、权益比例或合并范围不明确；
- 公司发生重大资产重组、业务剥离或并购；
- 套保方向和经营暴露方向相互矛盾；
- 行业默认和公司披露的价值链角色冲突。

### 6.6 公司画像生命周期与双时点

公司画像不是一个永久静态标签。同一 `instrument_id` 在借壳上市、重大资产重组、控制权变更、主营资产出售、跨行业收购或新增重大主业后，可能对应不同的经营业务状态。系统必须增加 `business_regime_id` 和画像变更事件，不得用最新画像覆盖上市以来的全部历史。

时间治理采用双时点：

- `valid_from/valid_to`：业务状态在经济和会计口径上的适用区间；
- `knowledge_from/knowledge_to`：该画像版本被市场公开且经系统审核后可用于研究的区间。

例如借壳资产在 6 月 30 日完成交割、7 月 5 日公告，7 月 3 日的历史 DCF 仍只能使用当时可知的旧画像；7 月 5 日以后才可在审核通过后切换到新 regime。旧版本通过 knowledge interval 关闭并保留，不做原地覆盖。

普通产品扩展不必机械地产生新 regime。若新增业务仍在原合并范围和经营模式内，可在当前 regime 增加分部；若发生主营替换、控制权变化、重大合并范围变化，或新业务达到设定的收入/利润/资产材料性门槛，则进入 regime change 复核。候选变更事件只能形成预警，不能提前停用当前 approved 画像。

## 7. 与现有模块的工程衔接

### 7.1 主数据

- `industry_memberships` 提供估值日申万一级、二级、三级归属；
- 商品主数据提供规范 `commodity_id`、单位和市场；
- 文档主数据提供公告、附件、报告期和可得日；
- 公司基础档案保留在 `company_profiles`，复杂业务事实单独建表。

### 7.2 期货与特殊商品行情

- `futures_exposure_mappings` 可承接已批准的 company/industry 到期货序列映射；
- `futures_spread_definitions` 和 `futures_spread_values` 承接加工价差；
- 无合适期货时允许映射现货、行业价格或公司披露售价序列；
- 行情序列缺失不应删除业务事实，只影响 DCF 驱动 readiness。

### 7.3 DCF 输入 bundle

新增 `business_profile_context`：

- `industry_default_profile`；
- `company_specific_profile`；
- `segment_profiles`；
- `approved_exposures`；
- `candidate_exposures`；
- `model_scores` 与 `conflicts`；
- `profile_version`、`data_available_cutoff`、`lineage_hash`。

DCF 仅消费 `approved` 且可得日不晚于估值日的事实。候选数据只展示在 diagnostics。

### 7.4 API

当前已实现本地只读接口：

- `GET /api/v1/research/company/{instrument_id}/business-profile`；
- `GET /api/v1/research/company/{instrument_id}/business-profile/history`；
- `GET /api/v1/research/company/{instrument_id}/commodity-exposures`；
- `GET /api/v1/research/company-profiles/review-queue`。

后续受权运维接口：

- `POST /api/v1/research/company-profiles/{instrument_id}/review`；
- `POST /api/v1/research/company-profiles/sync`。

读取接口不得隐式抓取网络；同步接口返回任务和数据质量报告。

## 8. 数据质量与时点规则

1. 优先记录真实公告日；缺失时允许按 A 股法定最晚披露期限估算，但必须标识 `estimated_conservative`。
2. 估算日期不能写回原始公告字段，也不能声称是实际发布日期。
3. 业务事实以公告可得日进入历史版本；重述和更正公告形成新版本。
4. 半年报与年报可以更新业务结构；季度报告只有明确披露时才更新分部事实。
5. 数值必须保留原始单位、标准单位、换算公式和权益口径。
6. 不同报告中的产品名称需要稳定实体 ID，避免名称变化造成伪新增。
7. 多来源冲突必须保留全部证据并记录主源选择原因。

质量指标：文档获取率、文本可解析率、证据定位率、字段精确率、单位正确率、勾稽通过率、自动批准率、人工驳回率、历史覆盖率和 DCF 可用覆盖率。

## 9. 分阶段实施计划

### Phase 0：目录与样本基线

- 建立字段 catalog、商品词典、价值链角色和证据等级；
- 每个首期行业选 20-30 家代表公司，覆盖龙头、综合企业和异常披露格式；
- 盘点本地公告 PDF、文本和表格解析能力；
- 建立人工金标准，不直接全市场回补。

验收：字段定义无歧义，样本证据可回链，行业模板经人工确认。

### Phase 1：主营分部与产品映射

- 解析年报/半年报分行业、分产品收入成本；
- 建立公司分部、产品和价值链角色；
- 生成行业默认与公司证据对比；
- 只让高置信度分类事实进入 DCF 模型评分。

验收：首期行业公司级主营产品覆盖率不低于 80%，抽样精确率不低于 95%。

### Phase 2：商品与价差映射

- 将产品和原料映射到现有商品主数据；
- 建立行业默认、公司覆盖、冲突和审批流程；
- 生成加工价差定义并回补时序；
- DCF 同时输出行业模型与公司模型诊断。

验收：所有进入估值的映射都有证据、方向、角色、有效期和置信度。

### Phase 3：经营量、成本、产能与储量

- 按行业解析产销量、售价、单位成本、产能和储量；
- 建设单位换算和项目/权益口径治理；
- 将生产量和成本曲线接入周期预测；
- 对资源公司探索 NAV 与 DCF 交叉验证。

验收：数值事实可跨表勾稽，无法勾稽的事实不得自动进入生产估值。

### Phase 4：合同、套保与价格传导

- 解析长协、定价周期和套保信息；
- 建立价格传导滞后与转嫁能力框架；
- 用历史财务和商品序列做解释性校验，不将回归结果直接视为因果弹性。

验收：模型能解释短期套保影响和中期经营暴露的差异。

## 10. 工作量与风险评估

### 10.1 可行性

- 主营分部和产品分类：高可行，官方年报覆盖较好；
- 价值链角色：高可行，但需行业词典和少量复核；
- 产销量和产能：资源、钢铁、化工龙头中等至高可行；
- 单位成本：中等可行，披露口径差异明显；
- 储量与权益资源：中等可行，矿种和准则差异大；
- 精确商品价格弹性：低至中等可行，不能只靠文本，需要历史经营数据和结构假设；
- 合同与套保量化：中等偏低，许多公司只做定性披露。

### 10.2 主要风险

1. PDF 表格、扫描件和跨页表导致抽取错误；
2. 公司披露口径随年度变化，历史事实不可直接拼接；
3. 收入占比不等于利润或现金流敏感性；
4. 加工企业受价差、库存周期、长协和成本转嫁共同影响；
5. 单一商品映射会误判综合企业；
6. 大模型抽取存在幻觉，必须以证据定位和规则校验约束；
7. 全市场一次性回补会产生过大的人工复核队列。

### 10.3 成本控制

首期应采用“行业模板 + 官方表格优先 + 候选复核”的方式。规则明确、结构稳定的字段自动化，叙述性强或影响估值较大的字段保留审批。按行业上线后复用词典、解析器和校验规则，工作量会逐步下降。

---

## 11. 验收标准

1. 任一 DCF 使用的公司业务事实可追溯到原始公开文档和页/章节。
2. 行业默认与公司特定画像在存储、评分和输出中保持分离。
3. 多业务和上下游一体化公司不会被压缩成单一商品标签。
4. 未审核聚合标签、低置信度抽取和估值日之后信息不会进入生产计算。
5. 商品映射包含角色、方向、材料性、有效期和置信度。
6. 价差模型明确产品腿、原料腿、换算系数和数据时序。
7. 同一输入版本可复现相同 DCF 结果和 xlsx 底稿。
8. 每期同步报告覆盖率、冲突、失败、人工复核量和 DCF readiness 变化。

## 12. 当前实施状态与下一步

### 12.1 已实现的治理基础层（2026-07-16）

OpenSpec change `establish-a-share-business-profile-governance` 已建立并完成第一阶段工程实现：

- `research.db` 新增 `business_profile_evidence`、`company_business_segments`、`company_operating_facts`、`company_value_chain_roles`、`company_commodity_exposures` 五类规范化表；`company_profiles` 继续只承担公司基础快照，不承载复杂历史事实。
- 仓储入口支持稳定主键幂等写入、版本和 lineage hash、原始/标准单位并存、候选复核队列与全历史读取。
- 解析器按估值日同时检查事实 `review_status`、证据 `review_status`、证据完整性、`data_available_date`、事实有效期及行情序列有效性；任一门槛不满足时不得进入 DCF。
- 行业默认画像与公司特定画像分开返回。相同商品和角色下，公司级已批准暴露优先；未匹配的行业默认仍保留，冲突、评分和推荐策略显式输出。
- 已批准公司暴露在内存中投影为现有 `futures_exposure_mappings` 兼容结构，不复制期货行情或价差主数据，也不在读取/估值请求中写库。
- DCF 输入 hash、lineage、响应和周期诊断已包含 `business_profile_context`；画像库为空或不可用时返回结构化 readiness 并保留原行业回退，不隐式联网。
- 已实现画像、历史、商品暴露和复核队列四类只读 API。

### 12.2 当前生产数据边界

以上完成的是数据契约、治理门槛和 DCF 接入，不代表公司画像数据已经覆盖全市场。当前本地生产库尚未执行官方年报业务分部的系统回补，`futures_exposure_mappings` 的行业/公司映射也需要通过独立目录和审批流程逐批建立。因此：

1. 没有 approved 公司事实时，DCF 继续使用权威申万行业和既有财务模型，并明确输出 `insufficient_company_evidence`。
2. 不得把 BaoStock、行情库行业、公司简称关键词或聚合页面标签直接提升为 approved 商品暴露。
3. 不得因为期货序列缺失而删除业务事实；只应降低商品驱动 readiness。
4. 本阶段未实现自动审批、PDF/OCR 抽取、合同和套保量化，也未对生产数据库静默写入示例映射。

### 12.3 后续优先顺序

1. 建立 Phase 0 首批行业样本目录、商品词典、证据等级和人工金标准，每个行业先选 20-30 家代表公司。
2. 基于 CNInfo/交易所正式年报和半年报实现业务分部、产品及价值链角色候选抽取，并保留页码、章节和文档哈希。
3. 对煤炭、有色、钢铁、石油石化、基础化工和部分建材建立经过审批的行业默认暴露目录，再逐家公司形成覆盖项。
4. 生成并回补加工价差定义；随后推进产销量、售价、单位成本、产能和储量。
5. 在人工金标准精确率达到验收线后，再扩大到全市场增量维护和受权审批 API。

### 12.4 公开数据采集专项（2026-07-16）

已新增本地 OpenSpec change `build-a-share-business-profile-evidence-pipeline`，用于补齐当前治理基础层与生产数据之间的缺口。该 change 的边界是：复用现有 CNInfo/交易所公告发现、PDF 归档和 source manifest，建立首批周期行业金标准、版本化披露模板和词典、文档派生 artifact、候选事实抽取、受控本地审核、增量维护及字段级质量门槛。

详细主备源、五类对象获取方式、解析分层、审核边界、维护频率、样本设计和工期评估见 `company_business_profile_data_acquisition_execution.md`。在项目具备管理接口鉴权之前，审核写操作只通过受控本地工具开放，不新增无鉴权 POST 接口。

### 12.5 公开数据采集第一批基础实现（2026-07-16）

- 已增加 `company_business_profile_regimes` 和 `company_business_profile_events`，分部、经营事实、价值链角色和商品暴露增加 `business_regime_id`、`knowledge_from/to` 及 supersession 字段。
- resolver 已按业务有效区间与知识有效区间选择 active regime。借壳交割早于公告时，公告前的历史估值继续使用当时可知旧画像；候选重大变化只产生复核预警。
- 同一估值时点若存在两个以上 approved active regime，resolver 不再按排序任取一个，而是清空 active regime、排除所有 regime 绑定事实，并输出 `overlapping_active_business_regimes` readiness blocker。
- 已实现年报全文/摘要/修订版、经营数据、资源报告、重大合同、套保和画像变化公告分类器；借壳、重组、收购、出售、控制权及主营变化只生成事件提示，不自动切换画像。
- 已实现 CNInfo 公司级文档发现 adapter，复用统一股票身份解析、分页、重试、限速、水位和公告审计；发现阶段不下载 PDF、不写业务事实。
- 已实现业务画像 PDF 不可变归档服务：共享 source manifest 显式记录 `source_tier`、公告发布时间和 `supersedes_source_file_id`，归档路径包含公告 ID 与 SHA-256；同一公告同一内容重跑短路，修订稿或附件变化建立新版本且不覆盖旧原件。
- 归档批次支持 `max_documents` 和原子 checkpoint；中断后按公告元数据指纹续跑，完整批次结束后清除 checkpoint。归档阶段只写原件和 manifest，不写 candidate/approved 业务事实。

- 已建立包含文档、页/表证据、产品、商品、单位、业务 regime、画像事件和审核决定的金标准 JSON Schema。
